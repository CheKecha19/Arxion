# Firewall Compliance: функциональная документация

## Проверка требований доступа по снимку

В разделе «Доступ → Матрица доступа» есть прямые команды для редактирования
требований, сверки области и выбора снимка устройства. Требования видны от
источника и от назначения. В редакторе можно искать по ID, политике и сервису.
«Заданные пары» показывает только пары с требованиями или закрытыми областями.
Из строки пары можно перейти к нужной карточке. Вкладка «Сетка» показывает
выбранную часть осей, включая пустые пересечения. Выберите ячейку и нажмите
«Добавить требования к паре». Та же форма открывается через «Задать несколько
сервисов» в редакторе. Чтобы найти пустое пересечение в заполненной матрице,
задайте фильтры обеих осей. Например, для пользовательской сети и DNS-01 введите
`tcp/53` и `udp/53` на отдельных строках. Предпросмотр покажет, что добавится,
и укажет связанные требования для совпадений и противоречий. Политику можно
задать позднее. Для закрытых областей исключения выбираются отдельно.

Если требования уже заведены в таблице, откройте «Вставить из таблицы» в
редакторе. Скопируйте столбцы `ID`, `Откуда`, `Куда`, `Сервис`, `Требование` и
при необходимости `Политика`, `Исключения`, `Зона источника`, `Зона назначения`.
Можно оставить заголовок с этими названиями. Источник и назначение указываются
по ID или однозначному имени существующей группы. Для сервиса используйте,
например, `tcp/443`, `udp/53`, `tcp/*` или `ip`. Действия принимают значения
`permit`, `allow_optional`, `deny`, `unregulated` и `boundary`.
Для закрытой области перечислите ID разрешённых требований через запятую.
Они могут находиться в этом же списке или в текущем черновике.
Политику можно оставить пустой до получения нужного снимка. Предпросмотр
проверяет строки, показывает новые записи и пропускает точные повторы.
Подтверждение добавляет строки в черновик выбранной области.
Утверждение новой версии сохраняет изменения в истории.

«Черновик из правил» в обычном редакторе открывает
список сохранённых политик проекта или площадки. Выберите конкретный источник,
затем найдите взаимодействия по адресу, группе, сервису или правилу. Можно
отметить всю текущую выборку и проверить основания отдельных строк.
«Добавить отмеченные» переносит только отмеченные взаимодействия как «Доступ
допустим» и добавляет необходимые адресные группы. Существующая группа
используется, если её явные адреса совпадают и такая группа одна.
Команда «Утвердить и сохранить» записывает новую
версию требований.

В редакторе проекта нажмите «Выбрать политику из снимков…», чтобы найти ID
по имени устройства, зоне или облачному ресурсу. Доступны последние сохранённые
политики выбранной области, включая VMware Edge Firewall и поддержанные SG.
Если у ID несколько источников, конкретный снимок выбирается при общей сверке.
Для политики без сохранённого снимка ID можно указать вручную.

Чтобы назначить одну сохранённую политику нескольким строкам, нажмите
«Назначить политику» в редакторе проекта. Поиск показывает требования и
закрытые области с пустым назначением в выбранной области. Отметки сохраняются
при смене запроса. Выберите политику, проверьте список изменений и подтвердите
их. Если выбранное назначение нарушит ссылку на исключение, окно покажет ID
закрытой области и разрешения. Например, R07 можно оставить без политики как
общее исключение для двух точек R15 и отдельно назначить политику транзитной
точке. Для сохранения назначений утвердите новую версию.

Чтобы создать правило «Только перечисленный доступ», отберите разрешения в
таблице требований и нажмите «Создать ограничение из требований». Можно
использовать одну строку или всю текущую выборку. Общие поля заполняются
автоматически. Если назначения или сервисы различаются, укажите охват
ограничения явно. Например, для R13 выберите общую внутреннюю сеть и
протокол IP, а R01–R06 оставьте в списке исключений. В редакторе ограничения
можно фильтровать исключения по группе источника и назначения и включить
все показанные строки. Эти фильтры помогают выбирать строки по группам.
Пересечение адресных условий определяется при сверке.

Когда одно ограничение проверяется в нескольких местах, в редакторе создайте
по закрытой области на каждую точку и объедините их во вкладке «Общие
ограничения». У точек совпадают группы, сервис и область, а политики и пары
зон задаются отдельно. Чтобы добавить вторую точку, выберите «Копировать
в другую точку». Можно дать точке название и оставить её политику
пустой до получения конфигурации. В сверке области кнопка «Закрытые области»
открывает сводку и основания каждой точки.

Для R15 из примера «Север» укажите внутреннюю сеть, SW-ACCESS-01 и TCP/22.
В обеих точках используйте R07 как разрешённое взаимодействие без привязки
к политике. Для транзитной точки выберите USERS-IN, для точки управления
оставьте политику пустой до получения снимка SW-ACCESS-01. Сводка показывает
лишнее разрешение в USERS-IN и отдельно указывает, что точка управления не
проверена. Если разрешение исчезнет из нового снимка, это изменение видно
в сравнении транзитной точки. Для окончательного вывода по управлению
нужны его собственные данные.

Команда «Сверить область» по умолчанию проверяет
утверждённую матрицу 2.0.0 на последних сохранённых ревизиях устройств и
контекстов. Если один ID политики есть в нескольких ревизиях, строка показывает
кандидатов. Устройство и контекст можно выбрать для одной строки или сразу
для неоднозначных строк той же политики. Следующая сверка ищет последнюю ревизию
выбранного устройства. После повторного открытия окна используются явные
назначения последней актуальной сверки той же утверждённой версии и площадки.
Для исторического среза выбор делается отдельно. Для выбора «Все площадки» проверяются требования
области проекта. Требования отдельной площадки доступны при выборе этой площадки.
JSON сохраняет сделанный выбор, исходные идентификаторы и контрольные суммы,
версии и все обработанные строки. Сохранённый JSON можно открыть в той же области.
В «Срезе» можно выбрать сохранённый файловый запуск и использовать его вместе с
операциями, завершившимися к его началу. Версия матрицы, каталог, назначения
площадок, профиль и сеансы берутся из входов новой сверки. Сравнение сохранённых
сверок показывает условия требования, причины и основания до и после изменения.
После актуальной сверки в истории выбирается предыдущая завершённая или частичная
запись той же версии, если она есть. Для исторического среза при сравнении
учитывается дата выбранного запуска. В окне сравнения сначала видны изменения и
пробелы. Можно найти любую строку по ID, группе или сервису и открыть основания
обеих сторон. Фильтры выделяют устранённые и новые отклонения, подтверждённые
сопоставимыми локальными оценками. Если изменились адреса каталога, это ограничивает
сравнение зависимых строк. Строки со ссылками на объекты устройства требуют
отдельной проверки состава объектов, если конфигурации различаются. Сводка
закрытых областей открывает сравнение каждой точки. Полный HTML включает все
строки и основания. Строки без изменений свёрнуты.
На вкладке «Находки в снимках» можно выбрать устройство или перейти из строки
матрицы к её источнику. Открываются проверки тех же двух сохранённых снимков.
Например, здесь виден дубликат ACL, который перестал обнаруживаться, даже если
оценка требования не изменилась. Вывод об исчезновении зависит от полноты и
сопоставимости проверок. При резком сокращении числа правил, неполном снимке
или смене профиля отображаются ограничения сравнения. Для прямого облачного
сбора без отчёта запуска доступно сравнение требований. В HTML из этого окна
экспортируется сравнение матрицы. Отдельный отчёт по находкам доступен через
сравнение запусков в «Изменениях».
В актуальной сверке предупреждение указывает, если более поздняя попытка того же
источника или файла не обновила использованный снимок.
CSV содержит все строки текущей выборки. В общую
сверку также входят явно выбранные политики из сохранённых сборов Cloud.ru
Advanced, Evolution и VMware. Для площадки используется привязка из самого сбора.
Старый сбор VMware без такой привязки доступен для прямой сверки всего проекта.
При повторной сверке той же области подготовленные индексы правил и полное покрытие
неизменившихся условий переиспользуются при точном совпадении ревизии. При изменении
группы учитывается фактический состав вложенных групп и адреса каталога в выбранном
контексте. Неизменившиеся составы, вычитания исключений и результаты оценки
применимости VLAN ACL берутся из ограниченного кэша. Пересечения требований и
состав исключений проверяются заново. Если появился новый снимок политики,
покрытие по нему вычисляется заново, в том числе для закрытых областей.

В сводке области строка показывает источник, назначение, сервис и результат.
Введите «Бухгалтерия» в поле «Откуда», чтобы просмотреть её доступы. Для списка
источников доступа к 1С введите «1С» в поле «Куда». Поиск по имени или ID группы
можно сочетать с фильтром результата. CSV выгружает все совпавшие строки.
Фильтр «Требуют внимания» открывает отклонения, конфликты требований, частичное
покрытие, строки с недостающими данными и ограничения применимости ACL. Для выбранного результата видны
политика, строки источника и первый доказанный фрагмент адресов, протокола и порта.
Если фрагментов несколько, рядом указано их количество. Карточка показывает
первые основания и примеры разных действий. Все основания доступны в полном JSON.
Из строки можно открыть «Разобрать путь» по сохранённому снимку Aruba или
Comware. Если политика уже связана с ревизией коммутатора, открывается она.
Для строки с несколькими кандидатами или без найденной политики предлагаются
доступные в той же сверке снимки, включая коммутаторы без ACL с сохранёнными
сетевыми фактами. Для таких коммутаторов общая сверка сохраняет компактную
ссылку. Полный снимок читается при его выборе и сверяется с контрольной суммой
сохранённого JSON. Старые сверки с прежней контрольной суммой читаются как
раньше. SQLite без JSON1 использует полные снимки при создании сверки.
Разбор показывает настроенные интерфейсы,
общий VLAN или маршрут и данные, которых не хватает для дальнейшего вывода.

Матрица 2.0.0 различает необходимый и допустимый доступ. Закрытая область задаётся
группами, сервисом, областью и политикой. Явно выбранные разрешения вычитаются из
её условий. Разрешение к адресу без карточки ресурса учитывается, если адрес
попадает в заданную область. Пустая пара вне закрытой области нерегламентирована.

Группа может ссылаться на логическую сеть или ресурс реестра. Для стандартного
контекста коммутатора адреса и площадку можно подтвердить в карточке ресурса.
Для конкретного коммутатора, UserGate, Ideco или политики Cloud.ru откройте строку
с однозначно выбранным источником и нажмите «Подтвердить адреса ресурса…».
Выберите карточку из групп строки, укажите IP или CIDR и сохраните. Сверка
перезапустится. Адреса применяются к указанному источнику и площадке, а для SG
учитывается конкретный интерфейс. На Aruba AOS-CX и поддержанных привязках Comware
логические сети и адреса ресурса используются в VRF конкретного VLAN ACL, когда
эта привязка подтверждена конфигурацией. Один ресурс может иметь разные адреса
для разных VRF. Сохранённая сверка показывает VRF и фиксирует использованный состав.
Для старых снимков AOS-CX с явно заданным `vrf attach` нужен повторный импорт.
Если VRF привязки неизвестен, сверка покажет пробел в составе группы.

Сверка показывает покрытие требования, противоположные условия и разрешения за
пределами согласованного перечня. Для поддержанного привязанного ACL применяется
порядок известных правил. Локальный результат относится к обращениям через
выбранный ACL. Отчёт сохраняет режим и полноту каждой оценки. Проверка полного
пути, NAT и прикладных прав требует дополнительных данных.

Для UserGate и Ideco в карточке требования или ограничения выберите «Зоны
политики» и укажите источник и назначение. Сверка учитывает объявленные
правила этой пары, включая правила с общим условием на одной из сторон.
Неоднозначные условия сохраняют неопределённость. Разрешение-исключение
закрытой области должно относиться к той же паре. При импорте черновика из
правил можно указать конкретную пару. При переносе без выбора пары точные
пары из правил сохраняются в отдельных строках.

Для маршрутизируемого VLAN ACL отдельная отметка показывает, что часть условия
может относиться к одному L2-сегменту, сервису самого коммутатора или другому
интерфейсу. Сверка сохраняет результаты локальной политики и ссылки на привязку.
Сравнение версий различает изменения статуса и видимых оснований, включая эту
отметку. Полный отчёт сравнения можно сохранить из предпросмотра.
Предпросмотр «Черновик из правил» также доступен в сверке отдельного снимка.
В списке предложений показываются разрешения, для которых известны условия.
Исходное правило и ревизия сохраняются в основании строки. Выбранные
взаимодействия нужно проверить перед утверждением.
В сверке отдельного снимка кнопка разбора пути подставляет конкретные адреса из
доказательства или из сохранённого требования, когда адрес однозначен.
Для требования с сеансом используется его подтверждённый адрес.

В общей сверке кнопка «Сеансы…» позволяет добавить офлайн-снимки офиса и VPN,
задать время оценки для каждого сетевого контекста и назначить сеансы требованиям
выбранной версии. Так оба подключения можно сверить в одном запуске, даже если
они используют разные VRF. Каждый сеанс сопоставляется только с политикой своего
подтверждённого контекста. История и JSON сохраняют снимки и назначения. В CSV
со сведениями о сеансах видны адрес, время, контекст и ссылки на свидетельства.
Вывод об адресе относится к выбранному сеансу и остаётся частичным для всей группы.

Вкладка «Цепочки доступа» связывает последовательные взаимодействия. Например,
первый участок может ссылаться на требование до прокси, второй — обозначать
участок от прокси до внешних ресурсов, для которого ещё нужны данные. Участкам
назначаются сохранённые сверки одной утверждённой версии матрицы и области.
Можно использовать сверки разных устройств. В JSON сохраняются выводы и
происхождение по каждому участку. Связь участков по группам описывает ожидаемый
путь, а работу прокси и фактическое прохождение трафика подтверждают отдельно.

Кнопка «Цепочки доступа…» в общей сверке подставляет результаты участков из
открытой сводки. Она показывает устройство и снимок для каждого найденного
участка. Для отсутствующего или неоднозначного результата видна причина. JSON
разбора сохраняет контрольную сумму общей сверки и её ID при открытии из истории.

В разборе цепочки можно сохранить шаблон и загрузить записи наблюдений из
офлайн JSON. Каждая запись содержит `step_id`, `context_id`, `source_ip`,
`destination_ip`, `protocol`, для TCP и UDP `destination_port`, а также
`outcome` и `origin` с `source_name`, `record_id` и `observed_at`. Поддержаны
исходы `connected` для TCP, `response_observed`, `denied`, `timeout` и `unknown`.
Для пользовательского требования добавьте `session_id`. Адреса, сервис и
контекст сопоставляются с сохранённой сверкой участка. Тайм-аут оставляет
причину неопределённой. Для зонального требования добавьте `zone_pair` с
`source_zone` и `destination_zone` из наблюдения.
Для цепочки, открытой из общей сверки, наблюдение сверяется с точной сохранённой
ревизией участка. Если исходный снимок недоступен, приложение показывает пробел.

Если внешний источник явно зарегистрировал завершение всей транзакции, можно
добавить `transactions` с `trace_id`, `origin`, `started_at`, `completed_at`,
`outcome` равным `completed` и ссылками `samples` на записи по `source_name` и
`record_id`. В каждой связанной записи нужен тот же `trace_id`. Совпадение всех
участков по порядку, времени и промежуточным IP/контекстам подтверждает указанную
попытку. Обобщение на весь диапазон доступа требует других свидетельств.

В редакторе можно закрепить версию набора требований за несколькими группами.
Вкладка «Группы» позволяет создать по группе для нескольких сетей или ресурсов
каталога за один раз. В карточке существующей группы можно добавить несколько
ссылок сразу. Адреса по-прежнему раскрываются при сверке в её сетевом контексте.
После явного объединения карточек ссылки из ранее утверждённой матрицы ведут к
активной итоговой карточке. Сохранённые результаты сохраняют использованные адреса.
При копировании или назначении набора отметьте группы в поиске либо вставьте
их ID. Можно отметить все найденные группы. Предпросмотр показывает добавление,
изменение, удаление и конфликты. Действующее назначение позволяет менять состав
групп с сохранением версии набора и ID оставшихся строк. Переход на новую версию
набора подтверждается отдельно. Изменения вступают в силу после утверждения матрицы.

Для правила с условием пользователя выберите группу, офис или VPN и требование
к устройству. «Свидетельства о сеансах» принимает офлайн JSON со сведениями о
членстве, устройствах и соединениях. Для сверки выберите время с часовым поясом
и конкретный сеанс. При подтверждённой связи пользователя, устройства и адреса
приложение сверяет политику для этого адреса. Результат сохраняется как частичный
для всего требования. Один VPN-пул не подтверждает членство или активный сеанс.
Один сеанс можно назначить нескольким строкам с одинаковым источником и
условиями. Каждая строка отдельно сверяется с составом своей группы.

Снимок версии `1.0.0` задаёт `project_id`, `scope_id`, `context_id`, `captured_at`
и списки `memberships`, `devices`, `sessions`, `pools`. Каждая запись включает
`evidence_id`, `valid_from`, `valid_until` и `origin` с `source_name`,
`record_id`, `observed_at` и необязательным `content_sha256`. Записи членства
добавляют `principal_id`, `group_id`, `member`, записи устройств — `device_id`,
`corporate`. Сеанс содержит `session_id`, `principal_id`, `device_id`, `channel`
(`office` или `vpn`), `assigned_ip` и при наличии `pool_id`. Запись пула
содержит `pool_id` и `prefixes` в CIDR. Времена имеют явный часовой пояс.

В сохранённом результате можно искать по группам, идентификаторам требований
и правил и фильтровать по статусу. HTML и CSV содержат всю выбранную область
результата, включая другие страницы списка. Предпросмотр показывает первые 100
записей и размер выборки. JSON сохраняет полный артефакт для дальнейшего разбора.

Для снимка Aruba или Comware команда «Разобрать путь между IP» показывает
настроенный исходный интерфейс и известные кандидаты маршрута для двух адресов.
При совпадении в нескольких VRF можно выбрать контекст явно. Если назначение
относится к самому коммутатору или тому же сегменту, это видно отдельно.
Разбор подсказывает, какие наблюдения нужны дальше, и показывает строки
источника. Данные описывают настройки из снимка. Для проверки прохождения
пакета нужны рабочая таблица маршрутов, сведения о соседях и политики на пути.

В сохранённом сборе Cloud.ru Advanced или Evolution команда «Сверить группу
безопасности с матрицей» открывает выбор группы, подтверждённого интерфейса,
направления и семейства адресов. Для Evolution можно выбрать все назначенные
группы интерфейса и сопоставить их объединённые разрешения. Для одной полностью
подтверждённой группы Advanced приложение учитывает приоритет и действие правил
на известных адресах интерфейса для новых соединений. Если в сборе отсутствуют
приоритеты, состояния правил или подтверждение фильтрации, доступны объявления.
Итоговый доступ зависит от маршрутов, других фильтров и состояния соединения.

Для входящих новых соединений Advanced можно выбрать все группы интерфейса
и указать их подтверждённый порядок. Введите источник и ссылку на запись,
подтверждающую последовательность на момент сохранённого сбора. Приоритеты и
состояния правил должны быть известны для всех применимых групп. Расчёт сначала
учитывает порядок групп, затем приоритет правила и действие. Порядок назначений
из произвольного списка не используется как доказательство.
Общая сверка подхватывает порядок из сохранённой сверки того же облачного сбора
и области. При разных подтверждённых последовательностях потребуется уточнение.

Старые матрицы и сверки 1.0.0 читаются с исходной семантикой. Новый формат
сохраняется в существующих таблицах истории. Предыдущие версии и их контрольные
суммы остаются доступны. История редактора читает краткие сведения о версиях,
затем загружает выбранную матрицу. Сравнение сверок требует совпадения устройства,
области, требований, состава ссылок и зафиксированного профиля. Частичные и
несопоставимые результаты не подтверждают устранение расхождения.

В «Источники данных → Файлы и запуск» можно сохранить набор файлов или папку
как источник проекта. Папка перечитывается без обхода вложенных каталогов.
Источнику назначаются площадки, как для других подключений. «Обновить и проверить»
использует включённые источники выбранной области. Сохранённое сопоставление пути
и устройства используется при повторном сборе, а одинаковые имена файлов в разных
папках сами по себе не объединяют устройства. Ошибки чтения сохраняются отдельно
от состояния анализа. Повтор неуспешных элементов использует исходные пути
запуска. Если папку не удалось прочитать целиком, повторяется получение списка.

## Логические сети и привязки VLAN — 0.13.0

В **Инфраструктура → Ресурсы → Реестр VLAN** откройте «Логические сети»,
чтобы задать название, площадку, ожидаемый VLAN ID, подсети в CIDR и при
необходимости VRF. На вкладке «Обнаруженные VLAN» можно создать сеть из
выбранного VLAN коммутатора или подтвердить, изменить и снять привязку.
Совпадение площадки и VLAN ID отмечает предложение для ручного подтверждения.
VRF отображается как атрибут логической сети.

Чтобы создать несколько сетей, отфильтруйте наблюдения, например по имени
`CORE-01`, и нажмите «Подготовить сети из выборки». В предпросмотре видны
подсети интерфейсов VLAN, площадка, VRF и причины исключений. Отметьте нужные
строки вручную или кнопкой «Отметить подходящие из показанных». Для пакетного
создания устройству нужна назначенная площадка и однозначно распознанная
подсеть. Уже привязанные или неоднозначные VLAN можно разобрать по одному.
Созданные сети и их привязки записываются вместе. Из вкладки «Логические сети»
кнопка «Открыть группы матрицы» открывает редактор, где сети можно выбрать
через «Создать из каталога». Сети последнего пакета уже отмечены, если для
них ещё нет групп.

После создания сети из VLAN открывается карточка сети. Нажмите
«Подтвердить предложенные VLAN», чтобы выбрать несколько совпадений.
Перед сохранением видны устройство, обнаруженные подсети, результат
сравнения и источник. Выбранные привязки сохраняются вместе. Из списка
привязанных VLAN двойной щелчок открывает наблюдение с портами, IP-адресами
интерфейсов, подсетями и источниками.

Для привязанного VLAN приложение сравнивает известные префиксы IP-интерфейсов
из последней сохранённой ревизии с ожидаемым списком. Неожиданный префикс
показывается как расхождение с устройством и ссылкой на строки конфигурации.
Если исходник ещё не подключён, ссылка предлагает выбрать файл и открывает
строки после проверки совпадения SHA-256.
При отсутствии IP-интерфейса, ожидаемых подсетей или при неполных адресных
данных без обнаруженного расхождения показывается «Нет данных для сравнения».

Сети, привязки и история ручных изменений сохраняются в SQLite отдельно от
ревизий. Таблицы добавляются при первом сохранении сети. Существующая база
открывается без пересохранения конфигураций, формат JSON ревизий сохраняется.

## ArubaOS Controller — 0.12.0

«Операционные данные» можно открыть отдельный вывод `show ap active` и увидеть
счётчик AP. Просмотр не сохраняет вывод в ревизии и не влияет на анализ ACL.
Полная трансляция, выбор маршрута и DPI-классификация не вычисляются.

CLI предоставляет `controller-inspect` (JSON, CSV, HTML) и `controller-role`.
Для подтверждённого экспорта доступны `--complete-config`,
`--configuration-view effective` и `--node-path`. JSON ревизии содержит
необязательный `controller_inventory` 1.0.0. Схема SQLite не меняется.

## Импорт коммутаторов — 0.10.0

Для ограниченных срезов AOS-Switch/ProVision, AOS-CX 10.10, Comware 5.20 и 7.1
определение формата не требует ACL. Основания выбора сохраняются; конфликтующие
сильные признаки дают неоднозначность. Hostname не выбирает парсер. Аппаратный
type и предположение модели по имени разделены. Поддержка конструкций не
подтверждает совместимость со всеми моделями/прошивками.

Импорт разделяет объявления ACL/ACE и их применения. SSH/SNMP Comware,
control-plane VRF и вложенные SNMP community AOS-CX, authorized managers
AOS-Switch относятся к управлению. Явные ACE считаются один раз независимо
от числа применений. Management, unbound и unknown новых импортов не участвуют
в выводах о транзитном exposure/shadowing/достижимости. Отсутствие транзитной
политики обозначается ограничением, а не успешной проверкой всей сети.
Некорректные адреса не исправляются автоматически и не заменяются ANY.

Для HPE FlexFabric 5944/5945 Release 6622 импорт с подтверждёнными моделью и
релизом может связать входящий IPv4 `packet-filter` с VLAN-интерфейсом в области
`route`. Добавьте в импортируемый текст вывод `display version` с моделью и
релизом того же устройства. При явном порядке `config` матрица использует
первое совпадение по номеру ACE. Если ни одно явное правило не покрывает часть
условия, эта часть остаётся неопределённой. Объявления ACL доступны отдельно. `auto`,
фильтрация L2, конфликтующие применения и аппаратное состояние требуют
отдельных сведений. [Руководство HPE](https://arubanetworking.hpe.com/techdocs/Switches/FlexFabric/5944/5200-7938.pdf)

Карточка «Структура и политики выбранного устройства» показывает интерфейсы,
VLAN, агрегаты, стек, настроенные маршруты, управление, ACL, диагностику и строки
источника. При просмотре исходника проверяется SHA-256 и скрываются секреты.
У правил есть фильтр назначения. Отдельный режим карты «Структура коммутаторов»
показывает локальные объекты и предположения по описаниям независимо от ACL-карты.
Одинаковые VLAN/подсети не объединяют устройства автоматически. Настройки не
подтверждают link up, установленный RIB, аутентификацию или сквозную доступность.
Для внешних политик нужны конфигурации ядра/NGFW.

CLI `firewall-compliance switch-inspect CONFIG --format json|csv|html --output FILE`
экспортирует сведения без запуска проверок. `--complete-config` фиксирует заявление
оператора о полноте, не полноту грамматики. Обычный `analyze` сохраняет JSON stdout
прежнего отчёта и выводит switch-сводку в stderr. Общие CSV/HTML и пакетный отчёт
содержат сведения switch-импорта.

Совместимость: ParseResult получает необязательные `switch_facts` и
`switch_policies` с собственными `schema_version=1.0.0`; отсутствующие envelopes
читаются как неизвестные и не восстанавливаются по именам ACL. Опциональное
`Rule.policy_purpose` у legacy отсутствует при сериализации. SQLite хранит целые
ревизии в JSON: DDL-миграция не нужна, старые записи не переписываются. Строгим
внешним readers нужна поддержка новых полей; старые приложения не обязаны читать
новые envelopes. Версия парсера в ревизии различает поведение импорта.
Rule IDs по строкам сохраняются где возможно, но новые SNMP-применения добавляют
представления ACE; сравнение разных parser versions не доказывает изменение
конфигурации. Повторный импорт создаёт отдельную ревизию. Batch-report — 1.2.0.

## Назначение

Локальное рабочее место Windows для анализа экспортированных конфигураций сетевого оборудования, правил межсетевых экранов и выбранных облачных ресурсов. Основной интерфейс — PySide6/Qt; для автоматизации доступен CLI.

Приложение разбирает правила и объекты, выполняет выбранные проверки, сохраняет доказательства, историю и пользовательские решения, строит карты условий ACL и отчёты. Автоматического изменения конфигураций устройств нет.

Для Advanced доступен локальный расчёт одной группы или нескольких входящих групп с подтверждённым порядком | Рабочие соединения и сквозная доступность требуют сведений о маршруте и остальных фильтрах |

UserGate/Ideco принимают собственные API-снимки приложения, а не произвольные резервные копии производителя. Их NAT сохраняется как отдельные данные без анализа трансляций.

ArubaOS Controller включён в стандартный импорт с ограничениями, перечисленными выше. Juniper Junos/SRX и Huawei VRP не подключены к текущему каталогу.

Замаскированные адреса `ipN`/`ip#N`, неизвестные объекты, сложные или неподдержанные selectors сохраняются неизвестными; случайные адреса не подставляются.

## Первый анализ в интерфейсе

### Общая команда и источники (R2, 0.7.0)

Основная команда «Обновить и проверить» читает сохранённые источники в фоне. Если есть подключения, последовательно выполняет сбор Cloud.ru VMware/Advanced/Evolution и сохранённых UserGate/Ideco, затем обрабатывает подготовленные файлы. Настройки фиксируются до начала работы. VMware Edge проходит поддержанные FW-проверки; Advanced/Evolution остаются инвентаризацией. Выключенные проверки не выдаются за выполненные. Один источник с ошибкой не скрывает результаты остальных. Подготовленная схема файла проверяется на изменение байтов между получением и анализом; ошибки чтения и разбора сохраняются отдельно.

В диалогах UserGate/Ideco можно явно сохранить несколько именованных подключений. Сохранение пароля требует отмеченного согласия; пароль защищается тем же Windows DPAPI, что и облачные ключи. Сохранённый пароль используется только с неизменной конфигурацией подключения. Ручная выгрузка в выбранный файл сохраняется. Для повторного общего сбора NGFW создаются новые уникальные JSON-файлы в подкаталоге `collected` рядом с БД. Не удаляйте их до определения политики хранения; автоматическое удаление не вводилось.

Когда настроенных источников нет, команда предлагает файлы или явное повторное чтение путей последнего запуска. Чтение файла с диска не означает получение новой конфигурации с устройства. После определения формата проверка начинается автоматически, если не требуется подтверждение неоднозначного устройства.

Через «Площадки» можно назначить источнику одну или несколько площадок. Для нескольких выберите площадки слева с Ctrl/Shift, затем источники в таблице и нажмите назначение. «Снять назначения» возвращает источники в группу без площадки. При выбранной площадке команда собирает только назначенные ей источники и файлы; «Без площадки» выбирает неназначенные. Общий источник нескольких площадок обновляется целиком: фильтрация внутри произвольного API/VDC этим не обещается. Файл, добавленный при выбранной площадке, получает её явное назначение; существующее назначение устройства имеет приоритет. Для нового ресурса источника с одной площадкой назначение сохраняется после разбора; источники нескольких площадок не дают оснований автоматически распределить устройства между ними. Идентификаторы автоматических NGFW-источников разделены по source ID, чтобы одинаковые имена разных устройств не склеивались.

В «Настройки → Проверки» задаются пороги предупреждений о сокращении правил и ресурсов (1–100%, по умолчанию 30%). Сравниваются сохранённые известные счётчики: для правил — тот же device ID, платформа и версия парсера, для API дополнительно неизменная конфигурация источника; для облака — тот же конфиг и набор собираемых ресурсов/данных. Предупреждение не доказывает сбой, удаление или улучшение безопасности. Оно сохраняет предыдущую ссылку, оба числа и порог, отображается в диагностике и центре задач. Файловые предупреждения включаются в отчёт анализа, облачные — в экспорт исходного сбора; их объединение относится к R4. Отсутствующий счётчик не заменяется нулём. При предупреждениях о составе линия динамики не соединяет такой результат как сопоставимый.

«Задачи» показывает активные операции и существующую историю запусков/сборов, обновляемую фоном. Отмена запрашивается между файлами/источниками; выполняющийся парсер или текущий API-запрос не прерывается принудительно. Уже записанные результаты сохраняются. Частичный/неуспешный файловый цикл использует совместимый статус запуска `interrupted`, а точные статусы находятся в элементах и диагностике. Закрытие приложения не гарантирует завершения активного daemon-worker; восстановление прерванных операций относится к R5.

«Повторить неуспешные элементы» в центре задач подготавливает отдельный новый запуск: для файлов — только ошибки, отказы, отмены и частичные результаты; для API — повторное получение выбранного источника с текущими настройками подключения. Перед запуском показываются число источников/файлов и подтверждение текущего профиля. Область повтора определяется исходной задачей и явно обозначается независимо от текущего фильтра площадки. Исходные результаты и решения не переписываются.

В левом меню доступны «Обзор», «Анализ», «Инфраструктура», «Доступ», «Отчёты»,
«Источники данных» и «Настройки». В «Доступе» находятся правила, матрица и сетевые
инструменты. История проверок доступна в «Анализе», а файлы и облачные сборы —
в «Источниках данных». Настройки проверок разделены на firewall, управление
устройствами и параметры профиля. PT остаётся запланированной интеграцией.

Обзор показывает критичность и динамику. График прерывается при неполноте или
изменении состава устройств, профилей и версий. Таблица источников различает
получение данных и анализ, последнюю попытку и последний успешный сбор.

Первый запуск полного цикла инициализирует историю профилей в worker с резервной копией. Snapshot настроек и ссылка на версию профиля сохраняются атомарно с запуском. Для cloud-результатов сохраняются те же ссылки при включённой истории. Новых внешних JSON-версий AnalysisResult/AclMap/DeviceRevision не вводилось; source ID/fingerprint и состояние сбора добавлены к settings запуска. Публичные параметры NGFW находятся в существующих integrations с ключами `ngfw:<provider>:<uuid>`, секреты — отдельно в protected_secret. Проверки runtime/CI текущего среза ещё не выполнены.

### Основа нового рабочего пространства (R1, 0.5.0)

Кнопка «Площадки» открывает явные назначения устройств выбранного проекта физическим площадкам. Можно создать/переименовать площадку, выбрать несколько устройств и назначить площадку или снять назначение. Массовое назначение сохраняется одной транзакцией. Проекты остаются исходными областями истории и автоматически в площадки не превращаются.

Селектор «Область просмотра» предлагает все площадки, нераспределённые устройства или одну площадку. Он ограничивает известные устройства, реестр, находки, правила, историю, сравнение и проектную карту. Облачный инвентарь и ручные карточки с неизвестной площадкой остаются видимыми. Расширенный анализ, сохранённые карты и полные отчёты сохраняют область исходного проекта или запуска. Выбор площадки не изменяет исторические снимки и не сужает полный экспорт. При просмотре истории используются текущие назначения площадок.

В том же окне «Сохранить версию настроек проверки» фиксирует текущие сохранённые параметры проекта: выбранные checks и management/policy-профили. Изменения в форме настроек сначала следует сохранить обычной командой приложения. Неизменный профиль повторно не нумеруется; показаны номер и fingerprint последней версии. После инициализации истории новые запуски атомарно фиксируют использованную версию и её fingerprint. Параметры подключения и секреты в эту историю не входят.

Чтение окна не меняет схему БД. Первая явная запись площадок/истории профилей выполняется фоном и создаёт резервную копию рядом с SQLite (`.before-sites-…sqlite3` или `.before-profiles-…sqlite3`), затем транзакционно добавляет собственные таблицы метаданных. Legacy user_version=1, старые запуски, ревизии и marks сохраняются. При ошибке инициализации операция сообщает об отказе; копия сохраняется. Для отката закрыть приложение и восстановить совместимую копию БД; автоматическое обратное преобразование не предусмотрено. При наличии org_context legacy-запись блокируется до явного переноса метаданных.

В проектной карте адрес сопоставляется с ресурсом только внутри его адресного контекста и снимка. Равные IP разных VDC, сетей или локальных устройств не объединяются автоматически. Сохраняются имена и aliases источника; неоднозначность не разрешается выбором случайного имени. Префикс подсети не становится адресом машины. Межустройственная общая адресная область требует явного основания.

Это основа нового рабочего пространства с совместимым хранением legacy origins. Активация org_context не выполняется: перед ней требуется явный перенос новых метаданных в организационную модель. Сквозной сбор по площадке и единая навигация относятся к R2, перенос решений — к R4. Работа приложения с этими изменениями пока не подтверждена CI или запуском.

1. Создайте или выберите проект.
2. Через «Добавить данные» выберите файлы либо папку конфигураций.
3. В «Проверки → Файлы и запуск» проверьте распознанные платформы, ID устройств и предупреждения.
4. В «Настройки → Проверки» выберите проверки и задайте организационные требования.
5. Нажмите «Запустить проверку файлов». Ошибка одного файла сохраняется отдельно и не превращается в успешный пустой результат.
6. Изучите «Проверки → Проблемы», связанные правила, источники и ограничения.
7. В «Отчёты» выберите конкретный запуск и экспортируйте результат.

Окно показывается до фоновой загрузки проекта. Сводка, реестр и история используют общие сведения о запусках и облачных наблюдениях. Облачный ресурс остаётся в реестре, если его видели в предыдущем сборе. Карточка читает полную запись выбранного ресурса, а «Облачный сбор» открывает полный снимок выбранной операции. В проектном списке правил отдельно загружаются записи с правилами, NAT или правилами групп безопасности. Проектная карта строится в фоне при открытии и показывает, если часть облачных данных недоступна.

| Раздел | Назначение |
|---|---|
| Обзор | Сводка ресурсов, выполненных проверок, находок и операций |
| Инфраструктура | Накопленный реестр, ручные подписи, размещение, архивирование и восстановление |
| Проверки | Находки, правила/объекты, подготовка файлов, облачный сбор и расширенные инструменты |
| Изменения | История запусков и сравнение; общая история операций также доступна через «Задачи» |
| Отчёты | Выбор запуска, сохранённые общие результаты, экспорт |
| Настройки | Правила и интеграции |

Наличие ресурса в инвентаре не означает выполненную проверку. Отсутствие ресурса в следующем сборе автоматически не удаляет его историю. Ручные подписи и решения хранятся отдельно от собранных фактов.

В реестре можно искать по имени, IP или CIDR. Поиск по адресу или сети учитывает известные IP из сохранённых конфигураций и облачного инвентаря, а также подтверждённые префиксы карточки. Наведите курсор на адреса, чтобы увидеть происхождение. Одинаковый IP может встречаться у нескольких ресурсов.

Обзор подсказывает действие для текущего состояния. На пустом проекте можно сразу выбрать файлы или папку либо открыть каталог интеграций. После сбора доступны ресурсы, результаты и матрица. Последние операции открывают выбранный запуск или сбор. Если одна команда обновила несколько источников, итог ведёт в центр задач, где каждый результат доступен отдельно.

Базовый policy-каталог содержит семь FW-проверок: any-any, дубликаты, полное затенение, объединение, logging, comments и disabled. Остальные включаются явно или отдельным workflow. Management относится к поддержанным HP/Aruba/Comware входам; к VMware Edge оно не применяется.

Профиль задаёт доверенные CIDR, административные цели и сервисы, запрещённые сервисы, пороги ширины доступа, исключения и необходимые привязки. Роль ресурса не выводится из имени/IP/комментария. Отсутствие требования не считается разрешением или нарушением.

Governance использует точную ревизию, явные metadata и статистику. Отсутствующий счётчик не означает отсутствие использования; отсутствие owner не выводится из комментария. Отдельный governance-этап не переписывает прежний policy-результат.

## Как читать вывод

| Состояние | Значение |
|---|---|
| `complete` | Проверка выполнена внутри заявленной поддержанной области |
| `partial` | Есть неизвестные/неподдержанные условия, неполные данные или исчерпан бюджет вычисления |
| `not_applicable` | Проверка неприменима к данному входу/требованию |
| `CHECK_NOT_EXECUTED` | Явная диагностика невыполнения; не успешный результат |

Отключённая проверка отсутствует в запуске. Ноль findings не означает безопасность. Parse coverage измеряет обработку конструкций внутри поддержанного среза, а не полноту всей конфигурации.

Finding содержит ID, критичность, объяснение, рекомендацию и Evidence: точную ревизию/правило, исходную строку или API object path, известные условия и ограничения. Для профильных проверок сохраняются версия и fingerprint профиля.

Пользовательские статусы и комментарии не меняют исходное finding; переходы решений сохраняются отдельно. Критичность — приоритет ручного рассмотрения, а не автоматически доказанная уязвимость.

## UserGate и Ideco

Сбор доступен из настроек интеграций и страницы файлов/проверок. Выберите профиль/узел, учётные данные и новый JSON-файл. Фоновый сбор добавит снимок в обычную подготовку анализа.

- UserGate: XML-RPC HTTP/4040 для UGOS 6.1.5+ и 7; проверяемый HTTPS/4443 для 7.3.3+. API-доступ на устройстве включается вручную. HTTP предназначен для защищённой сети управления/VPN.
- Ideco: classic v23 через проверяемый HTTPS, при необходимости свой PEM CA и порт; endpoint должен уже соответствовать нужному классическому контексту.
- Разрешены только login/logout и ограниченный набор операций чтения. Вход/выход могут создавать audit-события на устройстве.
- Пароли и session cookies не сохраняются в снимках. HTTPS не понижается автоматически до HTTP; отключения проверки TLS нет.
- Снимок из нескольких API-вызовов не является атомарным. Неизвестные selectors, динамические группы, расписания, users/L7/security profiles ограничивают анализ.
- Существующий выходной файл не перезаписывается. Ошибка локальной записи может оставить частичный файл.

```powershell
uv run firewall-compliance usergate-collect ngfw.local ug.json --family 7 --transport https --ca-file company-ca.pem
uv run firewall-compliance ideco-collect ngfw.local ideco.json --username admin
uv run firewall-compliance analyze ug.json
```

Пароль запрашивается интерактивно без отображения.

## Cloud.ru

Подключения задаются для выбранного проекта в «Настройки → Интеграции → Cloud.ru» отдельно для VMware, Advanced и Evolution.

| Платформа | Параметры |
|---|---|
| VMware | Адрес площадки, tenant, API Token; API version автоматически или явно; timeout |
| Evolution | Key ID, Key Secret, UUID проекта; timeout |
| Advanced | Постоянные AK/SK, IAM Project ID, регион; при необходимости адреса ECS/VPC |

Облачные ключи защищаются Windows DPAPI для текущего пользователя. Они не включаются в обычные настройки правил или экспорт истории. Для Advanced нужна синхронизация часов; временные AK/SK с Security Token не поддержаны.

После сохранения подключения откройте «Операции → Облачный сбор → Новый сбор», выберите источник, типы ресурсов и дополнительные сетевые данные. Сбор выполняется в фоне; частичные результаты и ошибки сохраняются.

VMware получает ВМ, Edge Gateway и Org VDC networks; дополнительно — сетевые подключения, Firewall, NAT и статические маршруты. Группы Firewall и профили портов читаются по ссылкам. Ресурсы доступны в границах прав токена; выбор отдельного Org VDC как фильтра сбора не реализован.

После VMware-сбора можно автоматически проверить Edge Firewall либо выбрать «Проверить правила сохранённого сбора». Повторный анализ сохранённого снимка не требует облачного ключа/сети. Находки попадают в общие проблемы, историю и отчёты.

Для общей сверки соберите Edge Gateway с данными Firewall. На вкладке «Результат → Ресурсы» выберите Edge Gateway и нажмите «Скопировать ID политики». Укажите его в требовании или точке контроля матрицы. Сверка читает сохранённый сбор напрямую, поэтому отдельный запуск проверок Edge не требуется. В карточке строки доступны ID сбора и Edge Gateway. Если известный источник политики недоступен, сверка покажет пробел. Чтобы проверить доступный источник с тем же ID, выберите его явно. Вывод касается объявленных правил Edge Firewall. Для вывода о маршруте, NAT и состоянии сервиса нужны дополнительные данные.

Advanced собирает ECS/VPC/подсети/SG; Evolution — ВМ/подсети/интерфейсы/SG. Это инвентаризация: SG-правила не становятся автоматически проверенными ACL. Данные NAT не трактуются как разрешение доступа.

## Карты и сетевые инструменты

Карта проекта связывает ресурсы и заданные условия правил с переходом к источнику. Уникальные IP ВМ сопоставляются только в известном VDC/подключении; одинаковый IP разных VDC не доказывает связь.

У карты проекта два представления. «Структура сети» показывает принадлежность и настроенные подключения ресурсов. Интерфейсы, сегменты и локальные TopologyLink берутся из сохранённых ревизий. «Условия правил» показывает направления и действия, заданные ACL между ресурсами. В структуре кнопка «Доступ» открывает условия выбранного ресурса. Для интерфейса используются правила его владельца. Сквозная доступность из этого не следует.

Панель карты проекта использует компактные элементы управления. Чекбокс «Легенда» показывает расшифровку линий, а его подсказка содержит счётчики и диагностику.

«ACL ревизии» открывает условия отдельных правил выбранного результата анализа, их порядок и источники. Сохранённые и пакетные карты доступны в этом режиме. «Топология» показывает интерфейсы выбранного устройства и привязанные к ним подсети с указанием источника. «Коммутаторы» показывает локальные настройки портов, VLAN и агрегатов, а также сведения о соседях с указанием основания связи.

Обзор агрегирует объекты до настраиваемого бюджета (по умолчанию 100 узлов и 200 линий). Группы представления раскрываются последовательно, связанные внешние объекты остаются отдельной сводной группой. Фокус скрывает посторонние узлы, линии и рамки. Линии листаются; все агрегаты текущей выборки доступны в таблице с именами/IP, сервисами, действием, полнотой и контекстами. Разные action/enabled/status и противоположные направления сохраняются отдельно. Линии категорий между одной парой объектов разведены. Полный исходный граф не сокращается.

«Назад» и «Вся карта» возвращают контекст и камеру в пределах сеанса. Лимиты и слоты узлов внутри зон сохраняются в опциональном `map_view_settings` существующего JSON настроек проекта; это кэш представления, не сетевая модель. Старые БД работают без него, некорректные записи кэша игнорируются. Подписи зон остаются в `map_zone_labels`; неприменимые после уточнения области подписи показываются отдельно и могут быть явно использованы повторно.

В реестре выберите ресурс и нажмите «На карте». Окружение открывается в отдельном окне, поэтому выделение, фильтры и прокрутка реестра остаются на месте. Для устройства показывается сохранённая конфигурация из карточки, для облачного ресурса — явные связи из его сбора. Если у ручной карточки подтверждены адреса и площадка, «Условия правил» показывает пересекающиеся источники и назначения с указанием владельца правила, контекста и исходной позиции. Эти совпадения описывают адресные условия. Принадлежность к VRF и доступность сервиса требуют собственных доказательств.

Для Cloud.ru VMware карта читает ссылки `routerRef`/`orgVdc`/`ownerRef`, а типизированные URN, href и UUID сопоставляет внутри одного подключения, типа ресурса и сбора. Явная принадлежность VDC отображается отдельно от сети и условий ACL. Если целевой объект не собран или ссылка неоднозначна, линия ведёт к обозначенному неразрешённому объекту с причиной. `vm_networks[].network` — локальное имя сети подключения ВМ: оно показывается, но не объединяется с Org VDC по одному имени. Для такого объединения нужна стабильная ссылка. Не собранные Firewall/сетевые подключения и ошибки нормализации отмечаются в диагностике карты. Реальная совместимость этого изменения с пользовательским снимком VMware пока не подтверждена.

На экранах правил, находок и условий карты есть явно применяемые фильтры source/destination IP/CIDR, протокола и портов назначения (например, `443,1000-2000`). CIDR и диапазоны означают пересечение, измерения объединяются через AND, порты требуют TCP/UDP. Неизвестные условия по умолчанию сохраняются с отметкой и могут быть исключены. Для находки достаточно совпадения одного связанного правила того же снимка. В raw cloud-правилах без нормализованного Rule соответствие фильтру остаётся неизвестным. Текстовый поиск находок включает evidence и связанные правила; карточка показывает порядок, политику и условия перекрывающих/перекрываемых правил.

Карта ACL хранит полную нормализованную ревизию и по одной связи на правило. Сохраняются allow/deny, disabled, unknown, порядок и provenance. Фильтры по ACL/правилу/действию/активности, source/destination CIDR, протоколу и destination port меняют представление, а не исходный снимок.

Выбор правила из полного поискового списка ACL строит отдельную сцену этого правила, даже если общий набор превысил бюджет. Выбор условия оставляет связанные правила; есть возврат и полный вид. Если даже одно правило имеет слишком много условий для сцены, сохраняются явное сообщение об ограничении и полный состав в карточке. HTML/JSON/DOT не сокращаются из-за фокуса Qt; PNG содержит текущую сцену с обозначенной выборкой.

CIDR-фильтр означает пересечение условий. Неизвестные условия по умолчанию остаются видимыми. Фильтры объединяются через AND; порт применим к TCP/UDP. JSON/DOT сохраняют полную карту, HTML может отражать фильтр, PNG экспортируется Qt-интерфейсом. Есть сохранение в SQLite и пакетное построение выбранных/всех результатов с отдельными ошибками.

«Анализ → Расширенные инструменты» предоставляет ограниченные ASA-сценарии импорта сетевых документов, выбора маршрута, локальных ACL/interface-решений и forwarding context. Metadata содержат явный источник/команду/время/полноту; команды не исполняются на устройстве.

Application binding и условный evaluator цепочки ingress/global/outbound/security-level существуют в ядре. Egress и доказательства отсутствия NAT/PBR/exceptions не угадываются. Сетевые оригинальные JSON можно экспортировать отдельно; обычный HTML policy-запуска не включает их автоматически.

Карта условий и локальное решение не доказывают полный путь через устройства. Сквозные reachable/blocked с effective NAT/PBR и operational state не вычисляются.

## Отчёты, контроли и совместимость

В 0.9.0 добавлен текущий срез R4: редактор матрицы доступа с группами, таблицей требований и сеткой «источник × назначение», история версий и сохранённых сверок. Группы задаются через карточку: IP/CIDR, ID объекта выбранной ревизии или вложенная группа. Сетка фильтруется по области, протоколу/портам и identity, а ячейка раскрывает все строки, включая конфликтующие. Она показывает явно заданные пары, без вывода членства AD и без интерпретации пустой ячейки как сетевого запрета.

Сверка выполняется для выбранной нормализованной ревизии и точной сохранённой версии матрицы. Режимы матрицы v2 описаны в разделе «Проверка требований доступа по снимку». В истории фиксируются нормализованные входы, версия профиля, ссылки на run/item и checksum. HTML-предпросмотр и HTML/JSON/CSV экспорт используют сохранённый результат. Открытие истории не создаёт таблицы; перед явной записью новой схемы создаётся резервная копия.

Из истории запусков доступны ручное сравнение двух проверок и выбор предыдущего полного сопоставимого запуска. Условия правил, сетевые факты, происхождение, нормализация, полнота и находки отображаются раздельно, с карточкой «было/стало/основание». Смена парсера/профиля и неполнота не выдаются за исправление, совпадение сигнатуры finding не доказывает идентичность правила. Сравнение выполняется в фоне и сохраняется в append-only историю с checksum; сохранённые результаты открываются без повторного вычисления. Экспорт выборки явно указывает фильтр и исключает полные ревизии скрытых устройств.

В Aruba AOS-CX и AOS-Switch после изменения файла находки могут сопоставляться
по однозначной позиции в том же ACL, если действие и нормализованные условия
совпадают. Карточка сохраняет ссылки на оба снимка. При неустановленном
соответствии сходных находок сравнение показывает неопределённость.
Для проверок дубликатов, затенения и объединения в подтверждённом Comware ACL
сопоставление также учитывает профиль применения и VRF. Номер исходной строки
остаётся ссылкой на конкретный снимок.

Единый отчёт запуска включает сохранённые сравнения, сверки отдельных ревизий и сверки области. Для исторической сверки связь задаёт выбранный запуск. Для актуальной сверки нужна строка оценки, использующая ревизию этого запуска. Сверка области сохраняет полный исходный охват, в том числе строки, оценённые по другим запускам и облачным сборам. Их происхождение показано в таблице.

Пакет отчёта 1.4 фиксирует дату формирования и полный охват запуска. Фильтры текущих таблиц к нему не применяются. В предпросмотре показывается до 100 строк каждой сверки области, начиная с расхождений и пробелов. HTML и JSON содержат все сохранённые строки из того же пакета. Если запись истории не прошла проверку, документ объясняет её отсутствие. Прежние пакеты продолжают отображаться.

Это промежуточная поставка R4 по запросу пользователя. Автоматический перенос/пересмотр пользовательских решений по dependency mapping, ограниченный режим «всё неописанное запрещено» и выборка общего отчёта ещё не подключены. Расписание R5 исключено пользователем и в поставку не входит. Существующие marks и история комментариев сохраняются отдельно; они не переносятся автоматически между запусками.

`AnalysisResult` объединяет сохранённые входы и компоненты одной операции: policy, поддержанные сетевые этапы, решения и ограничения. Компоненты сохраняют собственную область и точные входы; контейнер не делает их автоматически единым доказанным сетевым расчётом.

Общий результат экспортируется в JSON/CSV/автономный HTML и сохраняется в проекте. Экспорт сохранённого результата не требует полного исходного файла. Старые `FirewallAssuranceResult`, batch и сетевые JSON читаются своими readers; переименование полей не превращает их в новый пакет.

Технические контроли сопоставляют сохранённый AnalysisResult с версионируемыми требованиями организации, исключениями и каталогом. Показываются выводы и охват. Это не сертификация по NIST/CIS/PCI DSS; дополнительные справочные соответствия не заменяют утверждённую политику.

Структурный diff SR-005 разделяет значения, происхождение и полноту сетевых фактов. Отдельный policy/NAT/object diff нельзя считать готовым пользовательским сценарием только по наличию модулей.

Версии приложения, парсера, схемы и каталога сохраняются в результатах. Readers проверяют схемы, ссылки, целостность и воспроизводимость поддержанных компонентов; несовместимые данные не дополняются выдуманными defaults. Старые записи не переписываются автоматически новым анализом.

## CLI

```powershell
uv run firewall-compliance analyze "C:\configs\device.cfg"
uv run firewall-compliance analyze "C:\configs\device.cfg" --extended-policy-checks
uv run firewall-compliance analyze-bundle "C:\configs\device.cfg" --output analysis.json
uv run firewall-compliance analysis-export analysis.json --format html --output report.html
uv run firewall-compliance analysis-export analysis.json --format csv --output report.csv
```

`--management-profile`, `--policy-exposure-profile`, `--policy-scope-profile` принимают соответствующие JSON-профили. `--no-require-logging` и `--no-require-comments` отключают эти требования. `--complete-config` — заявление пользователя о полном экспорте, а не автоматическое доказательство полноты.

Группы `acl-map`, `controls`, `governance` предоставляют отдельные workflows; параметры уточняйте через `--help`. Код 0 у `analyze` означает сформированный результат, который может содержать findings/partial; ошибка чтения/распознавания/разбора возвращает 2. Проблемы определяются по JSON, а не только exit code.

## Хранение и источники

Основная БД: `%LOCALAPPDATA%\FirewallCompliance\projects.sqlite3`. Она хранит нормализованные снимки, результаты, пользовательские решения, историю и ограниченные фрагменты доказательств. Полный исходный файл автоматически не копируется.

Для полного просмотра источника или повторного анализа после перезапуска нужен исходник с прежним SHA-256. Другой hash означает новый вход; его нельзя показывать доказательством старой ревизии. БД и отчёты могут содержать чувствительные адреса/имена/выдержки.

## Структура реализации

| Пакет | Ответственность |
|---|---|
| `domain` | Типы, неизменяемые snapshots, provenance, полнота и валидация |
| `devices` | ASA/HP-Aruba/Comware, ArubaOS Controller, VMware/Advanced/Evolution |
| `checks` | Access, attachments, policy_quality, rule_hygiene, governance, management и общие операции |
| `analysis` | Каталог проверок, сетевые решения, diff и карты |
| `application` | Workflows, общий AnalysisResult, replay/экспорт, binding, controls и governance |
| `parsers` | Общие контракты/registry, compatibility imports, UserGate/Ideco |
| `infrastructure` | Общий I/O, Windows secrets, UserGate/Ideco API collectors |
| `interfaces` | CLI/Qt, workers, SQLite projects, представление и экспорт |

AOS-Switch/AOS-CX используют общую грамматику вендора. Старые пути импортов оставлены совместимыми. `qt_app.py` остаётся интеграционным центром; серверного REST API/web UI/repository в приложении нет.

Основные контракты находятся в [application/analysis_result.py](src/firewall_compliance/application/analysis_result.py), [domain/revision.py](src/firewall_compliance/domain/revision.py) и [parsers/catalog.py](src/firewall_compliance/parsers/catalog.py).

## Типичные затруднения

- **Формат не распознан:** сравните источник с поддержанным срезом; UserGate/Ideco требуют снимок своего коллектора.
- **Нет находок, но partial:** изучите ограничения; неизвестные условия могли исключить достоверный вывод.
- **Не открывается старый исходник:** подключите файл с исходным SHA-256; изменённый файл анализируйте заново.
- **Облачный сбор частичный:** проверьте права, доступность отдельных API и ошибки ресурсов; успешная авторизация не гарантирует права на все сервисы.
- **Невидимы нижние поля:** прокрутите страницу/редактор; крупные таблицы и панели имеют собственную прокрутку.
- **Portable не запускается после переноса:** переносите папку целиком с `_internal`, а не один EXE.

Правила защиты данных и границы security-review находятся в [SECURITY.md](SECURITY.md).
