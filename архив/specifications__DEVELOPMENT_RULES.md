# Правила разработки

Актуализировано 31.10.2026. Текущие рабочие ограничения определяет корневой
[AGENTS.md](../AGENTS.md); соглашения — [PROJECT_CONVENTIONS.md](PROJECT_CONVENTIONS.md).

## Приоритет до v1.0

Разрабатывать код приложения и запрошенные функции. Новые тесты, fixtures,
smoke-сценарии и тестовую инфраструктуру создавать только по прямому запросу.
Не расширять, не реорганизовывать и не удалять существующие тесты самостоятельно.
Автоматические проверки выполняются через GitHub Actions. Локальные тесты,
линтеры, форматирование/typing checks, harness, сборки и security checks требуют
явного запроса пользователя. Исходниковая сверка и обзор diff разрешены.
Непроверенный сценарий нельзя объявлять прошедшим проверку.

## Корректность и модульность

- Unknown/unsupported и отсутствие данных не означают безопасность.
- Сохранять diagnostics, source mapping, полноту и ограничения.
- Парсер преобразует формат в доменную модель; проверки возвращают CheckResult и не выполняют I/O.
- Vendor parsing/collection остаются в адаптерах; application оркестрирует сценарии.
- Доменные модели не зависят от UI/адаптеров; отчёты используют типизированные результаты.
- Изменения сериализуемых контрактов документировать в SCHEMA_MIGRATIONS.md.
- Не обновлять goldens ради прохождения проверки.
- Использовать синтетические данные; секреты и клиентские конфигурации не публиковать и не логировать.

## Организация работы

Небольшая задача: нужные исходники, изменение, обзор diff, краткий результат.
Существенная задача: scoped plan в PLANS.md, прямая проверка downstream consumers,
JSON/SQLite/Qt/runtime import контрактов; impact/context выполняются в CI.
Делегирование разрешено в пределах задачи и ограничений AGENTS.md.
Записывать значимые сборки/валидацию и их пределы в harness/build-log.md.
Не исправлять посторонние baseline failures без соответствующей задачи.

## Git и поставка

Каталог является Git-репозиторием. Workflow `.github/workflows/harness.yml`
выполняет отдельные проверки на Windows для PR, push в main и manual dispatch.
Наличие CI не означает успешный прогон: проверять фактические статусы и артефакты.
Commit/push/tag/публикация и доступ к реальным аккаунтам требуют разрешения.
Правила именования и версий: [GIT_RELEASE_POLICY.md](GIT_RELEASE_POLICY.md).
Единая Windows-поставка: [WINDOWS_DISTRIBUTION.md](WINDOWS_DISTRIBUTION.md).
Linux/offscreen результат не подтверждает native Windows release.
