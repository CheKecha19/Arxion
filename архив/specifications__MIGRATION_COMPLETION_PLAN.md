## Согласованный результат

Перенести фактически работающие возможности исходного прототипа в локальное Qt-приложение в согласованной области, сохранив CLI и новое ядро. Сначала завершить сценарии HP/Aruba AOS-Switch (AOS-S)/AOS-CX и Comware, затем добавить остальные форматы старого проекта согласно этапу 5. Первый приоритет backend — логическая карта заданных условий ACL между сетями и сервисами с трассировкой до устройства, правила и источника. Первый backend-срез добавлен по ADR-020; полный этап карты ещё не завершён. Это не effective reachability и не новая поддержка производителей. UI ведётся в отдельном чате.

Новые работы по Cisco ASA/IOS/XE отложены до отдельного решения: effective NAT/PBR,
расширение adapters и сетевых фактов, перенос ветки IOS ACL и Cisco network paths.
Задачи занесены в [BACKLOG.md](BACKLOG.md) и не блокируют текущий срез карты ACL или
приёмку согласованной области переноса. Существующие реализации, registry и tests
сохраняются; исторические завершённые задачи не отменяются.

Работа идёт по внутренним этапам с проверяемыми результатами. Пользователю поставляется один итоговый релиз после завершения всех этапов. Сроки определяются после декомпозиции задач; процент готовности по числу модулей не используется.

Дополнительная карта связей между устройствами использует конфигурации, необязательные LLDP/CDP-выгрузки и ручные подтверждения. Совпадение подсетей само по себе не доказывает физическое соединение.

## Общие правила реализации

1. GUI и CLI вызывают общие application services. Парсеры не строят отчёты; визуализатор не принимает аналитические решения.
2. Новые результаты имеют версии схемы, версии анализаторов, ссылки на ревизии, SHA-256 источников, evidence и полноту. До изменения контрактов оформить ADR и миграционные заметки.
3. Пользовательские статусы, комментарии, соответствия устройств и подтверждения связей хранятся отдельно от исходных результатов анализатора. Для изменений отметок добавить журнал с временем и предыдущим значением.
4. SQLite хранит нормализованные снимки, результаты и ограниченные выдержки. Полные конфигурации и сырые LLDP/CDP-документы автоматически не сохраняются. Нормализованные данные и отчёты также считаются чувствительными.
5. Просмотр сохранённых выдержек доступен без исходника. Дополнительные строки и повторный разбор требуют файл с совпадающим SHA-256; изменившийся файл создаёт новую ревизию.
6. `unknown`, `unsupported`, неоднозначность и неполнота не превращаются в разрешение, запрет или успешно пройденную проверку. Пустой список findings не доказывает безопасность.
7. Сохранение нового результата, его чтение после перезапуска и отчёт реализуются внутри соответствующего этапа, а не откладываются до финальной сборки.

## Этап 0. Зафиксировать объём и закрыть небольшие разрывы Qt

Создать проверяемую матрицу паритета: функция старого кода → новое API → экран/CLI → fixtures → критерий приёмки. Отдельно отметить реально работавшие сценарии, ошибочную семантику и декларации без реализации.

Восстановить в Qt открытие сохранённого `FirewallAssuranceResult` с проверкой схемы и экспорт существующего структурного diff ревизий. Открытый отдельный отчёт отображается как отчёт: из него нельзя выдумывать отсутствующий инвентарь устройства. Улучшение форм дополнительных ASA-входов отложено вместе с новыми Cisco-работами; существующий ввод сохраняется.

Критерий: все строки матрицы имеют целевой этап; старые JSON читаются; Qt даёт доступ к прежнему структурному сравнению без подмены сравнением findings.

## Этап 1. Логическая карта ACL — первый приоритет

Активный следующий шаг — backend логической карты заданных условий ACL на
существующих HP/Aruba AOS-S/AOS-CX и Comware результатах: нейтральный DTO, условия
и действия правил, ограничения и source mapping. Первый срез backend добавлен
по ADR-020: проекция, базовые фильтры, JSON с обратным чтением и DOT. Детали:
[ACL_MAP.md](ACL_MAP.md). Полный этап, сохранение в SQLite, сетевые фильтры,
HTML/PNG и нагрузочная проверка пока не завершены.
UI-сценарий ниже сохраняется в плане и реализуется в отдельном чате; новая поддержка
производителей и effective reachability не входят в этот срез.

Добавить раздел «Карта» с выбором запуска, устройства и ACL. Узлы показывают сети/адресные объекты и сервисы; связи показывают действие правила, условия и направление. Имена объектов из разных устройств не объединяются без явного основания.

Первый режим — отношения, заданные правилами. Разрешающие, запрещающие, отключённые и не полностью разобранные правила различимы. Для вычисленного решения внутри ACL учитывается порядок правил только в подтверждённой области анализа; неподдержанные условия дают неопределённость. Связь в этом режиме не обозначает сквозную сетевую достижимость.

Сценарий: открыть карту → отфильтровать сеть/сервис → выбрать связь → увидеть правила, объяснение и выдержки → перейти к устройству или открыть проверенный исходник. Предусмотреть поиск, масштабирование, перемещение, выделение связанных узлов, таблицу связей и панель подробностей справа. Начальный вид группирует данные по устройствам/ACL, чтобы большой пакет не открывался нечитаемым графом.

Использовать Qt Graphics View для desktop-карты и NetworkX для графовых операций. Графовый DTO не зависит от Qt. Автономный HTML содержит локальные SVG/JavaScript и данные; PNG создаётся из сцены, DOT экспортируется без обязательной установки Graphviz. Группировка адресов меняет только представление, не условия анализа. Сохранять настройки вида и положения узлов отдельно от результатов.

Критерий backend: карта заданных условий работает для текущих HP/Aruba AOS-S/AOS-CX и Comware fixtures, сохраняет allow/deny, disabled и ограничения; каждую связь можно проследить до правила и источника. Критерий UI в отдельном чате: данные 80 файлов доступны через фильтры без зависания UI; HTML открывается офлайн, PNG и DOT воспроизводят выбранный охват.

## Этап 2. Устройства и подтверждённые связи

Дополнить adapters HP/Aruba AOS-S/AOS-CX и Comware сетевыми фактами: интерфейсы, адреса, VLAN, привязки ACL и настроенные маршруты в явно поддерживаемом синтаксисе. Настроенные и наблюдаемые данные различаются. Расширение Cisco adapters отложено до отдельного решения.

Собрать версионированный снимок сети из выбранных ревизий. Каждая связь имеет тип и происхождение: наблюдение LLDP/CDP, ручное подтверждение либо конфигурационная гипотеза. Импорт LLDP/CDP поддерживает определённые текстовые форматы с fixtures, а не произвольный вывод любых устройств. Неоднозначное сопоставление имени/порта требует выбора; решения сохраняются с указанием ревизий и пересматриваются при изменении источников.

Карта устройств и карта ACL остаются отдельными режимами. Клик по устройству открывает его инвентарь, ACL, findings и конфигурационный источник. Отсутствие LLDP/CDP не мешает анализу ACL, но ограничивает выводы о физических связях.

Критерий: после перезапуска восстановлены снимок, evidence и ручные решения; одинаковые имена и неизвестные соседи не создают ложных соединений. Изменённый источник не используется как доказательство прежней связи.

## Этап 3. Сравнение правил и объектов

Добавить сравнение двух ревизий устройства: добавленные, удалённые, перемещённые и изменённые правила; действие, enabled, адреса, сервисы, logging, комментарии и привязки. Сравнивать содержимое объектов и групп, а не только их названия. Дубликаты имён и неоднозначные соответствия сохраняются в результате.

Изменение порядка отражается отдельно. Расширение/сужение разрешений вычисляется только там, где семантика условий и порядка поддержана; остальные случаи показываются как изменения без уверенного вывода о доступе. Смена версии парсера и неполный импорт видны пользователю. Неполный запуск не объявляет исчезнувшую находку устранённой; статусы автоматически не переносятся.

Критерий: изменение IP/порта объекта при прежнем имени, перестановка ACL, повторяющиеся имена и частичный импорт корректно отражены в UI и отчёте. Структурный diff, policy diff и динамика findings имеют отдельные обозначения.

## Этап 4. Дополнительные проверки и технические controls

Перенести работающие идеи старого аудита: небезопасные сервисы, широкие диапазоны портов, чрезмерно широкие разрешения, встречные разрешения, нарушения зон и доступ к критическим сервисам из недоверенных сегментов. Списки сервисов, пороги, management/trusted/untrusted-сегменты и ожидаемая политика задаются в проекте. При отсутствии обязательного контекста проверка сообщает о нехватке данных.

Перенести технические controls старых PCI/CIS/NIST-каталогов, проверив каждое условие. Привязка к именованному стандарту требует источника, редакции и точного ограничения проверки. Это техническая оценка выбранных controls, а не подтверждение соответствия организации стандарту. ISO/SOX-каталоги без реализованных проверок не считаются возможностями для переноса.

Риск отображается с объяснимыми факторами и охватом. Если переносится числовой score, методика версионируется, а непроверенные controls не учитываются как успешные. Зоны не угадываются по имени объекта, transport protocol не подменяет прикладной сервис.

Критерий: каждая проверка имеет положительные, отрицательные и неполные fixtures; deny/disabled не трактуются как открытый доступ. Заглушка и пустой каталог не дают «пройдено» или 100% соответствия.

## Этап 5. Остальные форматы старого проекта

Последовательно перенести UserGate JSON, Juniper и Huawei VRP. Проверка и перенос отдельной ветки Cisco IOS ACL из старого универсального парсера отложены в backlog до отдельного решения. Для каждого активного adapter зафиксировать формат/версию, source mapping, ограничения, golden и негативные fixtures. Это не обещание поддержки всех продуктов производителя; этап 5 не входит в ближайший срез карты ACL.

Первый Juniper-срез соответствует реально найденному старому парсеру: иерархические Junos firewall filters с `filter { term { ... } }`. Поддержка `set`-формата и SRX security policies не предполагается автоматически. UserGate начинает с подтверждённой структуры JSON-экспорта; Huawei VRP не объединяется с Comware.

Общий resolver поддерживает адреса, диапазоны, сервисы, вложенные группы и циклы любой длины. Неизвестная ссылка остаётся неизвестной, а не `any`; deny не теряется при импорте. Недостающие форматы ArubaOS controllers включаются только при подтверждении фактически работавшей ветки старого проекта; иначе это отдельное расширение поддержки.

Критерий: каждый подтверждённый старый формат проходит общий путь импорт → анализ → карта → diff → сохранение → отчёт. Поддержка объявляется по протестированным конструкциям, с явными отказами для остальных.

## Этап 6. Объяснимые сетевые пути

Завершить application binding сетевых входов к ревизии и evaluator последовательности route/interface/ACL-решений в отдельно подтверждённой области. Затем подключить межустройственные пути поверх снимка сети по мере появления необходимых фактов и проверенной семантики. Новые Cisco ASA/IOS/XE network paths, effective NAT/PBR и расширение adapters отложены в backlog до отдельного решения; существующие ограниченные ASA-сценарии сохраняются. Этот этап не является условием реализации логической карты заданных условий ACL.

Запрос «источник → назначение → сервис» показывает кандидаты путей, решение на каждом устройстве, доказательства, выбранный контекст и ограничения. Прямое направление и обратный трафик различаются. Отсутствующая ACL, неизвестный next-hop, неподдержанные NAT/PBR или недостаточные operational-данные не дают разрешение. Допустимые сценарии NAT/PBR реализуются отдельными проверяемыми срезами; остальные возвращают `unknown`/`unsupported`.

Графовый поиск пути остаётся поиском связей; итоговая достижимость требует проверенных решений всей цепочки. Отсутствие найденного пути в неполном графе не доказывает блокировку.

Критерий: fixtures покрывают разрешённый и запрещённый путь, ingress/egress, выбор маршрута, неизвестный сосед, отсутствующий контекст и неподдержанные преобразования. Работавший старый reachability API заменён объяснимым новым API и доступен из Qt/CLI без прежних ложных разрешений.

## Этап 7. Общий сценарий, отчёт и итоговый релиз

Объединить результаты завершённых этапов в версионированный пакет анализа. Сохранить совместимость отдельного `FirewallAssuranceResult` и чтение прежнего batch-report. Для переноса проекта между ПК предусмотреть отдельный пакет с нормализованными снимками, результатами и пользовательскими решениями, без полных исходников. Обычный отчёт не подменяет резервную копию проекта.

Дополнить HTML управленческой сводкой, охватом, картами, изменениями, controls и сетевыми ограничениями. Выдержки включены по умолчанию и отключаются настройкой. Все вставки экранируются, ресурсы локальные, печатный вид читаемый. JSON разделяет результаты анализатора и решения пользователя; графовые PNG/DOT остаются отдельными экспортами.

Подключить общий пакетный сервис к CLI: файл/папка, необязательная рекурсия, согласованный набор расширений, явный выбор поддерживаемого формата, audit/diff/controls/graph exports. Параллелизм добавляется только после измерений и с ограничением ресурсов. GUI остаётся отзывчивым; отмена снимает ожидающие задания, текущая операция завершается согласно возможностям ядра.

Итоговый пользовательский путь: открыть проект → выбрать папку → проверить форматы и предупреждения → запустить → получить сводку → открыть карту/находку/изменения при необходимости → экспортировать общий отчёт. Настройки и подтверждённые соответствия переиспользуются; обязательные дополнительные входы запрашиваются только для зависящих от них сценариев.

Критерий: один Windows-релиз проходит все проверки ниже; пользовательский гайд описывает реальные экраны и ограничения. Старый Tk интерфейс выводится из основного использования после закрытия матрицы паритета.

## Распределение работы между субагентами

| Направление | Ответственность |
|---|---|
| Интерфейс | Qt-карта, таблицы, панели подробностей, формы, навигация и доступность |
| Ядро и adapters | Графовый DTO, сетевые факты, resolver, policy diff, проверки, controls и пути |
| Хранение и отчёты | Миграции SQLite, история решений, снимки, JSON/HTML/PNG/DOT и пакет проекта |
| Интеграция и документация | Матрица паритета, общие GUI/CLI-сценарии, регрессии, сборка и гайды |

При доступных четырёх одновременных слотах основной агент координирует три подзадачи; проверка и документация выделяются в следующий проход. До параллельных изменений согласуются DTO и границы файлов. Завершение этапа подтверждается интеграцией, а не отдельными отчётами субагентов.

## Ошибки старого проекта, которые не воспроизводятся

- Allow и deny не рисуются одинаковым «разрешением»; enabled, порядок и область применения учитываются.
- Узкий CIDR не считается покрывающим широкий. Совпадение src/dst одного правила не доказывает встречное разрешение.
- Отсутствующий объект/ACL/маршрут не означает `any` или успешную достижимость; циклы групп диагностируются.
- Объекты одинакового имени на разных устройствах не смешиваются; изменение их содержимого не теряется в diff.
- Наличие любого default deny не доказывает действие этой политики на нужном интерфейсе и направлении.
- Заглушка control, пустой каталог и неполный анализ не дают успешную оценку.
- HTML не зависит от CDN и безопасно отображает специальные символы исходного текста.

## Приёмка итогового релиза

1. Каждая реально работающая функция старого проекта отмечена в матрице паритета с новым API, экраном/CLI и тестом либо явной отсрочкой Cisco до отдельного решения. Отдельно объяснены исправления прежних ошибок и отсутствовавшие реализации; отложенные задачи не отмечаются завершёнными.
2. Пакет порядка 80 файлов проходит без зависания UI; ошибки одного файла не прерывают остальные. Форматы, частичная поддержка и состояние проверок одинаково отражены в сводке и отчёте.
3. Перезапуск сохраняет проекты, результаты, карты, снимки, отметки, комментарии и историю их изменений. Полные входные документы не копируются; несовпадение SHA-256 блокирует доступ к старому запуску через изменённый источник.
4. Проверены deny/disabled/order, CIDR и порты, неизвестные ссылки, циклы групп, повторяющиеся имена, изменение объектов, частичный импорт и различие графового пути/достижимости.
5. HTML работает офлайн и при печати; JSON сохраняет версии и прежние контракты. Экспорты проверены на исходном тексте с HTML/JavaScript-символами. Пакет проекта восстанавливает нормализованные данные без исходных конфигураций.
6. Full HD, масштаб Windows 100–150%, длинные таблицы, клавиатура, видимый фокус, контраст темы, отмена и закрытие во время работы проверены на итоговой сборке.
7. Тесты ядра, parser contracts, CLI, интеграции, Ruff и mypy проходят. Проверены миграции базы и чтение прежних результатов.
8. Portable-сборка запускается на чистой Windows 10/11 x64 без Python и сети; выполнены проверка зависимостей и SBOM согласно правилам проекта. Наличие сборки на машине разработчика не заменяет эту проверку.

## Границы этого переноса

Web UI, сервер, collectors, автоматическое изменение оборудования, расписание и SIEM не входят в итоговый desktop-релиз. Автоматическая замена чувствительных данных отсутствует. Универсальная поддержка всех версий вендоров, произвольного NAT/PBR и всех L2/VRF-сценариев не заявляется.

CSV и матрицы доступа из целевых требований учитываются отдельными задачами развития: их отсутствие в проверенном старом рабочем сценарии не делает их условием паритета. Это не снимает соответствующие требования с общей дорожной карты.

Первый backend-срез карты выполнен по ADR-020: контракт, проекция, трассировка,
базовые фильтры и JSON/DOT. Следующий шаг — хранение и общий сценарий, затем сетевые
фильтры и остальные экспорты. Матрица паритета остаётся частью плана; UI карты
ведётся в отдельном чате. Этап карты не завершён и не означает effective reachability.
