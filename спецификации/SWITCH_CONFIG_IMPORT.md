# ТЗ: импорт конфигураций HP/Aruba и Comware

Дата: 08.11.2026. Требования реализуются в версии 0.10.0; состояние приёмки, фактические проверки и сборка фиксируются отдельно в PROJECT_STATUS.md. Наличие реализации не заменяет проверку критериев.

## 1. Цель и границы

Корректно импортировать конфигурации AOS-Switch/ProVision, AOS-CX 10.10, Comware 5.20 и Comware 7.1: отличать управление устройством от фильтрации транзитного трафика, извлекать конфигурационные сетевые факты и показывать их происхождение и ограничения.

Область — конструкции, представленные в четырёх разобранных конфигурациях. Поддержка этих конструкций не означает поддержку всех моделей и выпусков ОС. ArubaOS Controller/Instant, новые NGFW, effective NAT/PBR, вычисление полной сквозной достижимости и сбор с живых устройств в эту работу не входят.

Клиентские конфигурации, IP-адреса, имена пользователей, community и секреты не копировать в репозиторий или журналы. Примеры в реализации и документации — синтетические. Новые тесты и fixtures не создавать без отдельного запроса пользователя.

## 2. Исходное состояние

- `HpArubaParser` объединяет AOS-Switch и AOS-CX. Authorized managers уже помечаются как management, CX control-plane binding поддержан.
- `ComwareParser` распознаёт версии 5.20/7.1 при наличии ACL; SNMP-привязки учитываются, SSH-привязка основным ACL-разбором не учитывается.
- Основной Aruba ACL-разбор не связывает CX ACL с вложенными SNMP community.
- Управляющие записи входят в общий `rules`; общий счётчик интерфейса может восприниматься как число транзитных правил.
- Заголовок `!Version ArubaOS-CX ...` требует исправления детектора; сейчас конкретному примеру помогают признаки ACL/binding.
- Существующий контракт `NetworkFactsParser` ограничен ASA. Расширение сетевых фактов коммутаторов требует явного развития контракта, а не выдачи их за поддержанный ASA forwarding context.

## 3. Определение платформы

Разделять производителя, семейство ОС, версию, модель, тип оборудования и предполагаемую роль. Парсер выбирать по синтаксису ОС, а не по hostname, имени файла, наличию default route или слову Aruba.

| Семейство | Основные признаки | Адаптер |
|---|---|---|
| AOS-Switch/ProVision | HP Configuration Editor/hpStack, release-маркер, характерные команды | Существующий HP/Aruba, профиль AOS-Switch |
| AOS-CX | Заголовок `!Version ArubaOS-CX`, CX-синтаксис интерфейсов/ACL/VSF | Существующий HP/Aruba, профиль AOS-CX |
| Comware 5 | version 5.20, sysname, характерный Comware-синтаксис | Существующий Comware, профиль 5 |
| Comware 7 | version 7.1, sysname, характерный Comware-синтаксис | Существующий Comware, профиль 7 |

Требования:

1. Платформа определяется и при отсутствии ACL. Одиночная общая строка `version` недостаточна; использовать сочетание независимых признаков.
2. Поддержать пробелы, BOM и реальные формы комментариев заголовка, включая `!Version` без пробела.
3. Возвращать основания выбора и ограничения поддержки. Числовая уверенность отражает силу признаков, а не подлинность экспорта.
4. Конфликтующие сильные признаки разных ОС дают неоднозначность с объяснением, без выбора по порядку адаптеров.
5. Модель из аппаратного type сохраняется с источником; модель из hostname — только предположение. Ручной выбор профиля не отключает диагностику несовместимого синтаксиса.

## 4. Политики и области применения

Ввести явную типизацию назначения: `transit`, `management`, `unbound`, `unknown`. Назначение относится к привязке: одна ACL может иметь несколько применений. Одноимённые ACL разных устройств, типов и контекстов не объединять.

Сохранять объявление ACL/ACE отдельно от её применений: идентификатор, порядок, действие, адреса, протоколы, порты, семейство адресов, строки источника; для привязки — целевой сервис/интерфейс, направление, VRF и источник.
В AOS-CX исходная строка однозначного `vrf attach` VLAN-интерфейса сохраняется отдельно. Контекст маршрутизируемой IPv4 ACL подтверждается совместно строками применения и интерфейса. Для Comware используется VRF из подтверждённого профиля применения. При неоднозначном или неизвестном VRF адресный состав из другого контекста не подставляется.

Поддержать:

- AOS-Switch `ip authorized-managers`: источник, обычная маска, manager/operator, метод; это ограничение управления, а не транзитная ACL.
- Comware `snmp-agent community ... acl N` и `ssh server acl N`: связать с ACL независимо от порядка разделов. Учесть различия `user-interface`/числовых privileges в Comware 5 и `line`/ролей в Comware 7.
- Для HPE FlexFabric 5944/5945 Release 6622 сохранять подтверждённое входящее
  применение IPv4 ACL к VLAN-интерфейсу в области `route`. Порядок `config`
  позволяет вычислить первое явное совпадение. Остаток без совпадения остаётся
  неизвестным. Неподдержанное применение фиксировать с диагностикой и исходной
  строкой. [Справочник команд HPE](https://arubanetworking.hpe.com/techdocs/Switches/FlexFabric/5944/5200-7937.pdf)
- AOS-CX `apply access-list ip NAME control-plane vrf VRF`: сохранить точный VRF и control-plane назначение.
- AOS-CX вложенные `snmp-server community` → `access-level` и `access-list ipv4`: сохранить отдельные привязки community к ACL, не раскрывая значение community в обычном UI/логах.
- Поддержанные существующими адаптерами интерфейсные/VLAN-привязки транзитных ACL сохранить без регрессии.

Описание ACL `SSH`/`SNMP` не заменяет привязку. Объявление без распознанной привязки не считать действующей транзитной политикой. Отсутствующая ACL при наличии ссылки диагностируется отдельно.

Не смешивать маски: AOS-Switch authorized managers — netmask; Comware ACL — wildcard; AOS-CX — документированные формы адресов/префиксов. Сохранять исходную запись и проверенную нормализованную форму.

Явный deny и документированное неявное действие различать. Неявные действия определять только для подтверждённой семантики конкретного типа применения/ОС; не добавлять фиктивную строку исходника и не переносить автоматически транзитную first-match семантику на SNMP community/authorized managers.

Разделить счётчики: уникальные ACL, явные ACE, привязки, записи authorized managers, транзитные и управляющие применения, непривязанные и неразобранные элементы. Несколько community не умножают число исходных ACE.

## 5. Ошибки и полнота

- Некорректные адреса, включая запятые вместо точек, не исправлять автоматически и не заменять на ANY.
- Сохранять доступные неадресные факты и диагностировать повреждённые поля со строками источника; такие записи не дают доказанного разрешения.
- Различать неизвестное значение, неподдержанный синтаксис, отсутствие в документе и подтверждённое отключение.
- Полноту оценивать по областям: идентификация, ACL, привязки, управление, интерфейсы/VLAN, агрегация, маршруты. Успешный разбор нескольких ACL не означает полноту всей конфигурации.
- Файл без транзитных ACL — допустимый результат: «Транзитные ACL в представленном файле не обнаружены». Это не разрешение всего трафика и не подтверждение отсутствия внешних ограничений.
- Не считать импортированный файл автоматически полным running-config. Сохранять заявленную полноту, время захвата и происхождение; время импорта не заменяет время наблюдения.

## 6. Сетевые факты

Добавить отдельный слой фактов конфигурации, используя существующие модели там, где совпадает семантика. Не перегружать `Rule` VLAN, маршрутами или кабельными связями.

| Сущность | Извлекаемые поля |
|---|---|
| Устройство | hostname, ОС/версия, аппаратный type, источник модели, предполагаемая роль |
| Стек | stacking/IRF/VSF, участники, приоритеты, настроенные межсоединения |
| Интерфейс | исходное имя, тип, описание, shutdown/no shutdown, режим L2/L3, IP или динамический способ адресации, VRF |
| VLAN | локальный ID, имя/описание, tagged/untagged/access/native membership, allowed ranges/all |
| Агрегация | Trk/LAG/Bridge-Aggregation, физические участники, LACP, распределение по участникам стека |
| Маршрут | настроенный prefix, next hop, VRF/таблица, явно заданные параметры; отдельно default gateway управления |
| Управление | SSH/HTTPS/SNMP по VRF, источники доступа, AAA/fallback, локальные роли без паролей, NTP/syslog, OOBM |
| Дополнительные функции | наличие настройки DHCP snooping, STP, IGMP/PIM, broadcast forwarding; без заявления об их работоспособности |

Отсутствие shutdown не превращать в наблюдаемое link up. Динамический адрес хранить как способ получения, без выдуманного IP. Настроенный маршрут не считать установленным RIB, статический gateway не превращать в транзитный маршрут.

Общая VLAN с одним номером на разных устройствах не доказывает общий L2-домен. Совпадение IP-подсетей не доказывает физическую связь. Названия DMZ, Isolated, Unused и описание untrusted не задают доверие, изоляцию или фактическое использование автоматически.

## 7. Реестр и карта сети

Представлять три различимых слоя:

1. Настроенная локальная структура: устройство/стек, порты, LAG, VLAN, L3-интерфейсы, management plane.
2. Предполагаемые межустройственные связи по описаниям и сопоставлению идентичности; показывать основание и допускаемые альтернативы.
3. Наблюдаемые либо подтверждённые оператором связи — только при наличии отдельного свидетельства; текущий импорт не генерирует их автоматически.

Для связи хранить тип свидетельства, источник/ревизию, время, статус и конфликтующие данные. Ручное подтверждение не выдавать за LLDP-наблюдение. Исторические сведения разных дат не склеивать в безусловно актуальную сеть.

На карте показывать ядро и соседей как предполагаемые узлы, если они упомянуты только в description. Обозначать разрывы: отсутствует конфигурация соседа, неизвестен шлюз VLAN, нет RIB/состояния портов, неизвестна внешняя политика. Подсвечивать точки, для которых следующий полезный источник — конфигурация ядра или NGFW.

L2-канал между устройствами означает настроенный транспорт VLAN, а не разрешённое IP-соединение. Полную матрицу доступа и end-to-end reachable/blocked по этим файлам не строить. Допустим отдельный вид настроенной VLAN-связности с явными неизвестными участками.

## 8. Что видит пользователь

- Итог импорта: платформа и основания определения, версия, число политик по категориям, полнота и ошибки.
- Карточка устройства: интерфейсы, VLAN, агрегаты, стек, адреса управления, сервисы по VRF, маршруты и источники фактов.
- Правила: отдельные фильтры для transit/management/unbound/unknown; управление не включается в число транзитных разрешений.
- Карточка ACL: исходные ACE, все применения и переход к строкам источника без раскрытия секретов.
- Управление: матрица «сервис × VRF × источник × ограничение × достоверность», отдельно AAA и права. Разрешённый IP не означает успешную аутентификацию.
- Карта: физическая/логическая структура и предполагаемые связи с легендой доказательности; отдельно от ACL-карты разрешений.
- Отчёты/экспорт: те же категории, provenance, неизвестные области и счётчики, что в UI.

Примеры полезных наблюдений: сервис включён в двух VRF, ACL только в одном; описанный как Unused порт не имеет shutdown; парные серверные подключения по-разному входят в LAG; управляющий порт назначен VLAN данных. Это наблюдения/кандидаты на проверку замысла, а не автоматические нарушения без политики организации.

## 9. Совместимость и потребители

При реализации проверить `devices/network/hpe_aruba`, `devices/network/hpe_h3c/comware`, parser registry/management, domain/revision и сетевые контракты, application import/forwarding/acl_map, checks, infrastructure observations, Qt/CLI, JSON/CSV/HTML и SQLite history.

Management-правила исключить из транзитных exposure/shadowing/reachability выводов, сохранив специализированные management-проверки. Непривязанная ACL не становится действующей из-за попадания в общий массив.

Для новых полей определить версию схемы и миграцию до записи данных. Старые ревизии должны читаться без переписывания источников; новые недоступные в старых данных факты обозначаются unknown. Не восстанавливать назначение старых ACL по имени. Повторный разбор исходника создаёт новую ревизию, не меняет старые выводы и решения пользователя. Сохранять стабильную идентичность записей либо явно описать влияние на diff/history.

Не расширять существующий ASA forwarding-контракт молча. Новые L2/VRF/stack факты требуют самостоятельной совместимой модели и явного подключения потребителей. Документировать миграции в DOCUMENTATION.md и согласовать относящиеся NETWORK_INPUTS/FORWARDING_CONTEXT/DOMAIN_MODEL/ACL_MAP требования при реализации.

## 10. Критерии приёмки

1. AOS-Switch образец: 15 authorized-managers (7 SSH и 8 SNMP), 0 объявленных транзитных ACL; источники и методы разделены. Исправлен первоначальный ручной подсчёт 19.
2. Comware 5 и 7 образцы: по 2 управляющие ACL и 17 исходных ACE; SNMP и SSH назначения подтверждены привязками, 0 обнаруженных транзитных применений.
3. CX образец: 2 ACL, 8 исходных ACE, control-plane mgmt и четыре SNMP community binding. Повреждённые IP диагностированы; ACE не объявлены доказанными разрешениями. Control-plane ACL не переносится на default VRF.
4. Все четыре семейства определяются также по достаточным признакам конфигурации без ACL; конфликт платформ даёт объяснимую неоднозначность.
5. Стек, VLAN, LAG, порты, управление и маршруты представлены как конфигурационные факты со ссылками на источник. Предположения не становятся наблюдаемыми связями.
6. UI, карта, отчёты и сохранённая история согласованы по категориям и счётчикам. Секреты не появляются в обычном представлении и логах.
7. Существующие поддержанные транзитные ACL и чтение старых проектов сохраняют поведение; migration/unknown ограничения описаны.

Порядок реализации: идентификация и bindings → типизация/счётчики и потребители → сетевые факты/хранение → реестр/карта и отчёты. Это функциональные этапы одной области, не заявление о готовности полной сетевой модели.

Автоматическая валидация — существующие GitHub Actions и анализ их реальных отчётов; локальные проверки только по прямому запросу. Критерии выше не являются разрешением создавать тесты или помещать клиентские файлы в fixtures. Неисполненные и нулевые проверки не считаются успешными.
