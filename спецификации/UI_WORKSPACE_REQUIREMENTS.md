# Техническое задание: рабочее пространство анализа инфраструктуры

Уточнение 08.11.2026: в Инфраструктура → Ресурсы две вкладки — «Реестр ресурсов»
и «Реестр VLAN». Вкладка «Снимки и проверки» убрана по запросу пользователя;
история операций сохраняется. VLAN читаются из последних сохранённых конфигураций
в области проекта/площадки, с происхождением и подробностями подключений.
Одинаковый VLAN ID не является основанием объединять сети разных устройств.

«Логические сети» в реестре VLAN хранят ожидаемые подсети и ручные привязки
обнаруженных VLAN коммутаторов. Совпадение VLAN ID и площадки служит
предложением. По подтверждённым привязкам отображается сравнение с последней
ревизией, а из расхождения доступна строка источника.
Из карточки сети можно подтвердить выбранные предложения одним действием
и перейти к интерфейсам и IP-адресам привязанного VLAN. Ссылка на источник
предлагает подключить файл с совпадающим SHA-256, если его ещё нет в сеансе.
Логические сети можно создать пакетом из явно выбранных наблюдений VLAN.
В предпросмотре видны устройство, площадка, VRF, распознанные подсети и причины
исключения. Совпадения обрабатываются отдельно, а сети и точные привязки
записываются одной транзакцией. Из реестра доступен переход к группам матрицы.

## 1. Цель и основания

Обеспечить повседневный анализ инфраструктуры без обхода многочисленных вкладок ради отдельных действий. После однократной настройки пользователь запускает сбор и все применимые проверки одной командой, понимает полноту результата, разбирает находки и изменения, формирует единый отчёт.

Обязательные результаты переработки:

- понятный обзор состояния, актуальности данных и проблем;
- единый запуск по сохранённому профилю;
- обновление состава устройств без потери истории;
- сравнение снимков и результатов «было / стало»;
- читаемая карта при большом количестве связей;
- таблицы с карточками подробностей вместо одновременного показа всех технических данных;
- сопоставление имён, адресов и интерфейсов с сохранением контекста;
- требования доступа и их сопоставление с известными условиями политик;
- фоновая работа и периодические проверки;
- архитектурная возможность дальнейшего серверного исполнения.

Язык — русский, тема первого этапа — тёмная. Платформа — Windows desktop, PySide6/Qt. Сервер, Web UI, многопользовательский доступ и RBAC не входят в текущую desktop-поставку.

## 2. Границы работ

### 2.1. Переработка существующих функций

Навигация, обзор, загрузка данных, выбор проверок, просмотр результатов, карточки, фильтры, представления карт, история, экспорт. Существующие проверки и расширенные инструменты остаются доступны через контекстные переходы; сокращение навигации не означает удаления функций.

### 2.2. Новые прикладные возможности

Оркестрация полного цикла, стабильный каталог объектов и областей, профили с версиями, расписание, сопоставление результатов между запусками и пересмотр решений, требования матрицы доступа, общая проекция инфраструктуры. Наличие отдельных модулей в текущем коде не считается завершённым пользовательским сценарием.

### 2.3. Не входит автоматически

Автоматическое исправление конфигураций; подключение к реальным устройствам при разработке; новый произвольный набор API/SSH/AD-коннекторов; непрерывная обработка событий; гарантированная сквозная reachability; effective NAT/PBR; анализ неподдержанных платформ; отдельные виды отчётов по ролям; светлая тема; мобильное приложение; серверная миграция. Интеграция с каталогом AD и полный механизм проверки пути требуют отдельного определения входов и семантики.

Из реестра можно добавить несколько ручных ресурсов из таблицы после
предпросмотра. Имя, адреса и площадка задаются оператором. Пакет сохраняется
атомарно, с ручным происхождением и доступом из каталога групп матрицы.

## 3. Организация рабочего пространства

### 3.0. Схемы основных экранов

Общий каркас: слева навигация; сверху организация/область, выбранный запуск и «Обновить и проверить»; справа сверху центр задач. В рабочей части последовательно показываются краткий статус данных, основные сведения и контекстные действия. Настройки открываются без потери выбранного объекта.

Обзор: строка актуальности и полноты → показатели источников/устройств/проблем → диаграмма критичности рядом с динамикой → короткая таблица «Требуют внимания». Нажатие показателя открывает список с тем же запуском и фильтром. До первого анализа вместо графиков — шаг подключения источников.

Результаты: строка «запуск / область / профиль / полнота» → поиск и основные фильтры → таблица слева и сворачиваемая карточка справа. На узком окне карточка заменяет рабочую часть с кнопкой возврата к сохранённой выборке. Находки и диагностика выполнения проверок имеют отдельные переключатели, общий контекст сохраняется.

Карточка: заголовок/критичность/решение → объяснение → связанные объекты → условия и evidence → ограничения → действия и история. Для shadow условия двух правил сравниваются по одинаковым полям. Переход к правилу сохраняет ссылку возврата к находке.

Карта: компактный переключатель структуры/условий правил и фильтры сверху, полотно слева, список взаимодействий справа. Легенда включается чекбоксом, счётчики полного/отображаемого набора и диагностика доступны в его подсказке. Карточка связи открывается из строки/линии; «Назад» восстанавливает прежнюю раскладку. При превышении бюджета вместо густого графа показываются группы с раскрытием.

Подготовка: список источников и файлов со статусами → эффективный профиль → резюме ожидаемого охвата → запуск. Необязательные настройки не перекрывают основное действие. Изменения: выбор двух запусков → сводка сопоставимости → категории различий → парное представление значений. Матрица: версия/область → таблица требований → карточка строки и её оценки. Отчёт: выбор завершённого запуска/области → предпросмотр разделов и полноты → экспорт.

### UX-01. Область работы

Основная иерархия: организация → площадка → ресурсы. VDC, сегмент, виртуальная система, политика и интерфейс сохраняют собственную техническую принадлежность; VDC не приравнивается автоматически к физической площадке. Ресурс может быть не распределён по площадкам. Группы по роли и назначению являются дополнительными срезами, могут пересекать площадки.

В шапке постоянно видны организация, выбранная область, время результата и действие «Обновить и проверить». Область — вся организация, одна или несколько площадок; дополнительные фильтры применяются внутри разделов. При переходе сохраняются область и выбранный запуск. Несовместимый фильтр не сбрасывается молча: UI сообщает причину.

Дерево площадок раскрывается по требованию, имеет поиск и избранное; не загружает и не раскрывает все устройства автоматически. Названия и группы редактируются отдельно от исходных фактов. Роли пользователей на этом этапе определяют сценарии, а не механизм разграничения прав.

### UX-02. Навигация

| Раздел | Содержимое и основное действие |
| --- | --- |
| Обзор | Актуальность, полнота, проблемы, динамика, сбор; запуск или переход к разбору |
| Инфраструктура | Дерево / таблица / структура сети / карта доступа; каталог ресурсов и источников |
| Проверки | Находки, выполнение проверок, правила/объекты, запрос доступа, матрица |
| Изменения | Выбор снимков/запусков, различия и их основания |
| Отчёты | Единый отчёт по зафиксированному запуску и выбранной области |

Настройки организации, профилей, интеграций и расписания открываются отдельно. Глобальный центр задач содержит активные и завершённые операции, ошибки и повторный запуск. Не создавать второй независимый реестр истории: центр задач ссылается на те же сохранённые запуски.

Соответствие текущей навигации: «Операции → Файлы и проверки» входит в подготовку/центр задач; «Анализ → Проблемы» — в «Проверки»; карты и инвентарь — в «Инфраструктуру»; история — в центр задач и «Изменения». Правила, объекты, governance и технические контроли доступны из «Проверок» и карточек с явными ограничениями.

В текущем коде есть отдельный раздел «Сетевая карта» и три режима: связи по правилам, топология конфигурации и карта проекта. Их перенос должен сохранить существующие переходы к правилам, переименование зон и обновление сетевых фактов; это изменение общей навигации, а не удаление режимов.

### UX-03. Представление и состояния

Таблица предназначена для поиска, сортировки и выбора; карточка — для объяснения и доказательств. Второстепенные технические поля раскрываются по запросу. Настройки столбцов, ширины, сортировки и фильтров сохраняются для пользователя рабочего места.

Каждый экран имеет состояния: первоначальная настройка, загрузка, данные, пустой результат, нет совпадений фильтра, частичные данные, ошибка, устаревшие данные. Пустая выборка не обозначается как «проблем нет». Для каждого состояния есть пояснение и применимое действие.

Критичность, полнота и пользовательское решение визуально различаются; цвет всегда сопровождается текстом/символом. Поддерживаются клавиатура, видимый фокус, масштаб Windows и изменение размера окна. Длинные имена доступны полностью в карточке/подсказке. Интерфейс не требует различения только красного и зелёного.

## 5. Полный цикл и надёжность сбора

### RUN-01. Один прикладной сценарий

Последовательность: зафиксировать область и версии настроек → получить данные → сопоставить ресурсы → разобрать → оценить полноту → выполнить применимые проверки → сравнить → сохранить итог → обновить UI.

Ручной и плановый запуск используют один application-сервис. CLI по возможности вызывает тот же сервис без Qt. Изменение настроек во время выполнения не меняет уже начатый запуск. Сохраняются run ID, инициатор (ручной/расписание), источник, версии профиля/матрицы/анализатора и ссылки на входные ревизии.

«Полная проверка» означает все включённые применимые проверки сохранённого профиля, а не все определения каталога и не полное доказательство безопасности. UI сообщает о выключенных, неприменимых и невыполненных проверках, не смешивая их.

«Забытое правило» не является выводом по одному наличию правила. Кандидаты в неиспользуемые требуют поддержанной статистики с достаточным периодом наблюдения; просроченные разрешения — явных сроков/метаданных. Отсутствие счётчиков, владельца или дат не подменяется нулевым использованием. UI отдельно объясняет основание каждого такого кандидата.

### RUN-02. Источники и состав данных

Источники: поддержанные интеграции, выбранные файлы и папки. Автоматически подготовленный файл обрабатывается тем же импортом; режим наблюдения папки не считается обязательным без отдельного решения. Доступ через интернет использует только разрешённые поддержанные протоколы и проверку TLS; UI не пытается автоматически создавать связность или обходить ограничения сегмента.

Для каждого источника хранятся стабильный ID, тип, область, настройки без открытых секретов, ожидаемая периодичность, последняя попытка, последний успешный сбор и диагностика. Ошибка опроса, недоступность и неподдержанный формат различаются.

Сбор через API учитывает пагинацию, ошибки отдельных страниц/объектов, таймауты, ограничения частоты и повторные ответы. Частичная выгрузка не заменяет последний полный снимок как заведомо полный. Неатомарность нескольких вызовов отражается интервалом сбора и ограничением. Повторы не создают дубли одного ресурса внутри результата.

Файл читается как согласованный вход: при изменении в процессе чтения импорт отклоняется или повторяется с диагностикой. Сохраняется хеш прочитанного содержимого. Время импорта и mtime не выдаются за время наблюдения устройства.

### RUN-03. Контроль полноты

На уровнях источника, устройства, набора правил и проверки отдельно видны:

- получение данных и ошибки;
- полнота инвентаря, когда она доказуема;
- разбор правил/объектов и неподдержанные конструкции;
- применимость и выполнение проверок;
- давность и происхождение наблюдений.

Счётчики «получено», «распознано», «не обработано» сравниваются только при одинаковых единицах и известной базе. Процент не показывается при неизвестном знаменателе. Ноль правил может означать известное отсутствие, неприменимость, неизвестность или ошибку — эти состояния не взаимозаменяемы. Роутер без ACL остаётся на структурной карте; management-проверки применяются независимо, если поддержаны.

Резкое сокращение правил/ресурсов относительно прошлого сопоставимого снимка вызывает предупреждение и переход к сравнению. Порог задаётся в профиле; предлагаемое начальное значение 30% — параметр для согласования, а не доказательство ошибки. Предупреждение не удаляет данные и не заменяет доказательства полноты. Неполный новый результат не должен выглядеть как устранение прежних проблем.

### RUN-04. Фоновое выполнение и отмена

I/O, разбор, анализ, сравнение и подготовка крупных карт выполняются вне UI-потока. Обновление Qt-моделей происходит в UI-потоке. Центр задач показывает этап, обработано/всего при известном объёме, ошибки, время начала; для неизвестной длительности используется неопределённый прогресс.

Состояния задания: очередь, выполняется, запрошена отмена, отменено, завершено, завершено частично, ошибка, прервано завершением процесса. Отмена останавливает постановку новых работ и проверяется между безопасными этапами; неподдержанное мгновенное прерывание не обещается. Уже сохранённые результаты сохраняются с частичным статусом. Ошибка одного устройства не останавливает независимые устройства.

Результат позднего worker не перезаписывает экран другой организации/области. Во время анализа доступны прежние результаты с отметкой их даты. Ошибка повторного запуска не скрывает последний успешный. Повтор только неуспешных элементов создаёт связанный новый запуск, а не переписывает историю.

## 6. Настройки и расписание

### CFG-01. Версионированные профили

Профиль хранит набор checks и параметры: доверенные/запрещённые сети и сервисы, административные цели, требования logging/comments, пороги, привязки ACL, governance-метаданные, правила свежести и применимые исключения. Поля группируются по смыслу; дополнительные настройки раскрываются. Неподдержанный параметр не должен создавать видимость реально выполняемой проверки.

Проверяется формат CIDR, портов/диапазонов, обязательных данных и противоречий. У каждого параметра есть назначение, область действия и влияние на проверки. Перед запуском доступно краткое резюме эффективного профиля.

Начальная модель: один профиль организации и явное назначение профиля площадке/источнику. Приоритет назначения должен быть детерминирован и показан пользователю; скрытого слияния конфликтующих параметров нет. Изменение создаёт новую версию; старые запуски сохраняют старую. Матрица версионируется отдельно, но её версия фиксируется запуском.

### SCH-01. Периодический запуск

Режимы: вручную, каждые N часов (включая час), ежедневно в указанное время. Расписание содержит часовую зону, область, источники и ссылку на профиль; при старте фиксируется его конкретная версия. Показаны последняя попытка, успешный сбор и следующий запуск.

Desktop выполняет расписание только при работающем приложении и компьютере. Закрытие приложения сопровождается понятным уведомлением о приостановке расписания. После сна/перезапуска предлагается или автоматически выполняется не более одного пропущенного запуска согласно сохранённой настройке; бесконтрольная очередь пропущенных запусков запрещена. Переходы времени не создают дубликаты.

Пересекающиеся ручной и плановый сборы одного источника сериализуются; UI показывает причину ожидания. Число параллельных источников и повторы ограничены. При ошибке авторизации бесконечные повторы не выполняются. Повторный анализ старого файла обновляет время проверки, но не свежесть источника.

## 7. Обзор

### DASH-01. Состав

| Блок | Представление | Переход |
| --- | --- | --- |
| Сбор | Компактные показатели: успешно, ошибки, устарело | Список соответствующих источников |
| Инфраструктура | Известно / обновлено / проверено устройств; явно разные числа | Отфильтрованный реестр |
| Проблемы | Горизонтальные столбцы по критичности и число новых | Список находок |
| Динамика | График сопоставимых запусков, отдельные ряды новых/сохраняющихся/более не обнаруженных | Сравнение выбранных точек |
| Требуют внимания | Короткий список приоритетных находок и ошибок данных | Карточка |
| Текущий/последний запуск | Этап, время, полнота и ошибки | Центр задач / итог |

Временной график используется для динамики, столбцы — для сравнения категорий, таблица — для конкретных действий. Круговые диаграммы и гистограммы не добавляются без задачи распределения. Не использовать единый «процент безопасности».

Состояние конфигураций и полнота анализа отображаются раздельно. При смешанной давности устройств указывается диапазон и число устаревших; время последней попытки не заменяет время успешного получения данных. Изменения профиля, версии нормализации и области помечаются разрывом/аннотацией графика: уменьшение findings не объявляется улучшением без сопоставимости.

## 8. Каталог ресурсов и идентичность

### CAT-01. Сущности и принадлежность

Каталог связывает организацию, площадки, VDC/tenant, устройства/виртуальные системы, VM, интерфейсы, VLAN, подсети, адреса, политики, правила, сервисы и группы. Пользовательские/AD-группы — условия идентичности субъекта, а не подсети. Все связи имеют источник и достоверность.

ID ресурса не равен отображаемому имени или IP. Для внешнего объекта предпочтителен стабильный ID провайдера в контексте источника/tenant. Для IP контекст включает изолированное адресное пространство (VDC/VRF/tenant или явно установленную эквивалентную область). Для интерфейса обязателен владелец, для правила — устройство/виртуальная система и политика. Одинаковый IP, VLAN ID или имя в разных областях не объединяет объекты.

### CAT-02. Сопоставление

Показывать «имя машины + IP + контекст». Несколько интерфейсов/адресов принадлежат одному ресурсу только при наличии основания. Данные облака и ACL связываются при доказанном соответствии области и адреса в релевантное время; NAT-адреса не приравниваются автоматически. Неизвестная область или несколько кандидатов дают неоднозначное соответствие с объяснением.

Ручное сопоставление и подпись хранятся отдельно: кто/когда, причина, область действия. Они могут быть отменены без изменения исходного снимка. Старый отчёт не переименовывается молча при изменении текущего каталога. Несогласованные имена разных источников сохраняются как aliases с происхождением.

### CAT-03. Обновление состава

Перед подтверждением неоднозначного импорта доступны новые/совпавшие/конфликтные ресурсы. Исчезновение из сбора — «не наблюдается»; доказанное удаление требует полного сопоставимого инвентаря. Архивирование — отдельное пользовательское действие с восстановлением. История конфигураций и находок не удаляется вместе с исключением ресурса из текущего списка.

## 9. Карты

### MAP-01. Два представления

«Структура сети» показывает известную принадлежность и топологию: площадки/VDC, устройства, интерфейсы, VLAN, подсети и машины. Принадлежность к одной подсети не выдаётся за доказанную физическую связь. Межустройственные связи требуют отдельной общей модели; текущий TopologyLink внутри DeviceRevision не расширяется молча.

Автоматические визуальные группы адресов по /24 или /64 обозначаются именно как группы представления. Они не считаются фактически настроенными подсетями или VLAN; подтверждённые границы берутся из исходных сетевых фактов.

«Карта доступа» показывает заданные условия правил с направлением, действием, сервисом и ограничениями. Заголовок/легенда явно обозначают режим «Условия правил», а не «Подтверждённая доступность». Из объекта структуры доступно действие «Показать доступ».

### MAP-02. Фокус и масштабирование

- Начальный обзор использует агрегированные группы, а не все IP и линии.
- Выбор узла включает фокус: несвязанные линии и узлы полностью скрываются, а не остаются затенёнными.
- По умолчанию видны только непосредственные связи; более дальний уровень раскрывается явно.
- Переход из реестра открывает отдельное окружение ресурса по точному сохранённому источнику. Для карточки с подтверждёнными адресами и площадкой можно искать пересекающиеся адресные условия в сохранённых ревизиях этой площадки. Результат указывает исходное правило, контекст владельца и неизвестные условия.
- Большое число получателей группируется по выбранной иерархии площадка/VDC/подсеть; пользователь раскрывает одну группу.
- Цепочка навигации, «Назад» и «Вся карта» возвращают прежние фильтры и масштаб.
- Перерасчёт не переставляет без необходимости все неизменившиеся узлы; сохраняются раскладка и выбранный объект при совместимом обновлении.
- Разрешения, запреты и неизвестные действия имеют различимые типы; противоположные направления различаются.

Предлагаемый начальный бюджет вида — до 100 узлов и 200 отображаемых связей. Это настраиваемый параметр представления для измерения, не ограничение количества исходных данных. При превышении карта агрегирует и показывает скрытое количество; случайное молчаливое отбрасывание запрещено.

### MAP-03. Агрегация без потери смысла

Агрегированная линия хранит ссылки на исходные relation/rule IDs. Подпись показывает число уникальных правил с названием единицы. Если фильтр сервисов не выбран, линия обозначается «несколько сервисов», а не «любой сервис». Разные action, enabled и completeness не объединяются в одно однозначное разрешение; допустим составной индикатор с раскрытием категорий.

Исходная AclMap сохраняет контракт «одна relation на правило с наборами условий», без source × destination × service декартова размножения. Визуальные линии — отдельная проекция. Нельзя суммировать счётчики разных групп как число уникальных правил без дедупликации.

### MAP-04. Список взаимодействий и карточка

Рядом с картой доступна таблица «Источник / назначение / сервис / действие / контекст / полнота / основание». Выбор строки фокусирует связь; выбор связи фильтрует список. Это основной способ точного разбора объекта со 100+ соединениями.

Карточка связи содержит правила, устройства, источники, направление, интерфейсы/зоны при наличии, identity-условия, расписания, unsupported, время снимка. Каждая связь объяснима переходом к доказательствам. Пользователь/AD-группа без состава не превращается в список известных пользователей. Unknown не скрывается по умолчанию и не заменяется ANY.

Экспорт изображения отражает текущий вид с легендой, фильтрами, временем и ограничениями. Экспорт полного графа и текущей выборки различается явно. Существующие JSON/DOT-контракты не меняются под видом косметического изменения.

## 10. Находки, поиск и решения

### FIND-01. Таблица и карточка

Основные столбцы: критичность, проблема, устройство/область, решение пользователя, изменение между запусками. Фильтры: площадка/VDC, устройство, check, критичность, решение, полнота, новые/сохраняющиеся, адрес/подсеть, сервис и группа при наличии данных.

Карточка: понятное описание → причина → затронутые объекты/правила → сравнение условий → evidence → ограничения → рекомендация → история решений. Для shadow показать перекрывающее и перекрываемое правила, порядок, политику и условия покрытия. Для групповой находки показать список устройств и основания каждого включения.

Evidence открывается по проверенной ссылке на снимок. Если исходный файл отсутствует или его хеш изменился, UI показывает сохранённый допустимый фрагмент/позицию и объясняет невозможность чтения оригинала; произвольный путь из evidence не открывается как доверенный источник.

### FIND-02. Поиск

Поиск по имени/alias/IP/объекту/номеру правила ограничен выбранной областью, которую видно рядом. CIDR-фильтр имеет явно указанную семантику пересечения. Порт применяется с протоколом; отдельно можно искать диапазоны. Примеры запросов: где используется подсеть, какие правила относятся к серверу TCP/443, где встречается объект, какие находки появились после обновления. Естественно-языковой поиск не входит в обязательный объём.

### FIND-03. Решения

Нормализовать пользовательские состояния: не рассмотрено, подтверждено, ложное срабатывание, принятое исключение, требует пересмотра. Точное отображение существующих marks согласовать миграцией, не переписывая исходные findings. Комментарий обязателен для исключения и ложного срабатывания; для исключения можно задать срок пересмотра.

Решение сохраняет запуск, finding, ревизию, автора/локальную отметку оператора, время, причину и зависимости. Между запусками оно переносится только при доказанном сопоставлении и неизменности значимых зависимостей: правила, порядка/политики, связанных объектов/групп, профиля, матрицы и релевантной семантики проверки. Изменение или неизвестность зависимостей требует пересмотра. При отсутствии точного dependency mapping изменение связанной конфигурации консервативно требует пересмотра. Комментарии остаются историей.

«Исправлено» не выводится из отсутствия находки после неполного анализа. Пользователь может заявить исправление, но подтверждение повторной проверкой отображается отдельно. Массовые решения показывают число и область выбранных находок, применяются только к разрешённым состояниям и фиксируют историю.

## 11. Изменения

### DIFF-01. Сопоставимые основания

Сравниваются выбранные запуски, а на уровне устройства — конкретные ревизии. Для смешанного запуска видны времена каждого устройства; он не выдаётся за атомарный снимок всей сети.

Раздельно отображаются состав ресурсов, правила/объекты, сетевые факты, результаты проверок, полнота, происхождение, нормализация и профиль. Смена версии парсера не доказывает изменение устройства. Неоднозначное сопоставление правил показывается, а не превращается в удаление/создание по одному номеру строки.

Новые, сохраняющиеся, более не обнаруженные и неподтверждённые из-за неполноты findings различаются. По умолчанию выбирается предыдущий сопоставимый успешный запуск; основание выбора видно и изменяемо. Если сопоставимого запуска нет, сравнение не выдумывается.

Из сравнения матрицы можно открыть находки по двум сохранённым ревизиям того же
устройства, платформы и контекста. Для каждой стороны сверяется исходный элемент
запуска и отчёт. Сопоставимость отдельной проверки оценивается по её версии,
сохранённому профилю и полноте источников. Результат проверки не меняет вывод
об исполнении требования. Снимки без отчёта и смена источника видны как ограничения.

### DIFF-02. Влияние на доступ

Изменения source/destination/service/action/order и связанных групп показываются рядом. Формулировки «расширение/сужение условий правила» допустимы только в поддержанной семантике. Формулировка «доступ открыт/закрыт во всей сети» требует отдельного доказанного анализа пути. Сохраняется разделение SR-005: значения, provenance, normalization, completeness.

## 12. Матрица доступа

### MATRIX-01. Модель требования

Обязательные поля: ID, источник/группа, назначение/группа, сервис, требование (разрешить / запретить / не регламентировано), область. Дополнительные: пользователь/группа identity, расписание/условия, основание, владелец, срок пересмотра. Версия матрицы и история изменений обязательны. Сервисы имеют протокол и порты/диапазоны; ANY задаётся явно. Роли и состав групп не выводятся из имён/IP без декларации.

Группа может содержать явно заданные адреса, подсети и ссылки на объекты. При выполнении сохраняется использованный состав/версия; изменение каталога не меняет прошлую оценку. Неизвестное членство, циклические ссылки групп и конфликтующие требования диагностируются. Молчаливый приоритет строк запрещён; правило разрешения конфликтов должно быть явно задано либо результат остаётся неопределённым.

Отсутствующая строка означает «не регламентировано». Режим «всё неописанное запрещено» включается явно для ограниченной области с указанием охватываемых групп/сервисов; не создаёт выводов о неизвестной внешней инфраструктуре.

Матрица 2.0.0 различает необходимое и допустимое разрешение. Закрытая область
фиксирует источник, назначение, сервис и контекст политики и ссылается на явный
набор разрешающих требований. Проверяется остаток многомерных условий после их
вычитания. Адрес внутри этой области оценивается независимо от наличия отдельной
карточки ресурса. Ссылки на каталог фиксируются в артефакте сверки с использованным
составом. Версии 1.0.0 сохраняют исходную семантику.
Закрытую область можно начать с выбранных разрешений. Общие поля допустимо
предзаполнить. Различающиеся оси или сервисы требуют явного выбора охвата.
Выбор исключений поддерживает независимые фильтры точных групп и включение
всей текущей выборки. Адресное пересечение рассчитывается при сверке.

Версия набора требований закрепляется за выбранными группами. При создании и
замене назначения сначала показываются изменения состава. Утверждённые версии
матрицы сохраняют конкретные строки и ссылку на использованный набор.
Выбор групп поддерживает поиск и массовые отметки. Состав групп действующего
назначения можно изменить с сохранением выбранной версии и ID оставшихся строк.
Ссылки закрытых областей и цепочек проверяются до применения. Группы можно
создать из нескольких карточек каталога, по одной группе на карточку.
Обычный редактор позволяет открыть сохранённую политику из выбранного источника
и просмотреть предложения для черновика. Поиск и массовая отметка действуют
на всю выборку. Добавляются только отмеченные объявленные разрешения с типом
«Доступ допустим», исходным правилом, ревизией и необходимыми группами.

Для условия пользовательской группы, офиса или VPN, корпоративного или
конкретного устройства поддержаны офлайн-сведения с временем и контекстом.
Подтверждённый сеанс сужает адресный расчёт до его IP. Результат для сеанса
остаётся частичным для полного требования. Зависимое от пользователя или
расписания исключение нельзя вычитать из полной области по одному сеансу.

Сверка области выбирает последнюю сохранённую ревизию по устройству и контексту.
Неоднозначный ID политики показывает источники-кандидаты. Оценка выполняется
по выбранным требованиям и их зависимостям без полного произведения устройств
на строки матрицы. Выбор устройства, платформы и контекста может применяться
к строке или к неоднозначным строкам одной политики и сохраняется с результатом.
Результат можно выгрузить в JSON и открыть в той же области.
Сверки области хранятся с контрольными суммами и сопоставляются по утверждённой
версии матрицы. Смена устройства, контекста или наличия источника отмечается
отдельно от изменения локального решения. Подтверждённое изменение соответствия
требованию требует сопоставимых полных локальных оценок. Изменение состава
каталога влияет на сравнение зависимых строк, включая исключения закрытой области.
Интерфейс показывает изменения и пробелы первыми, поддерживает поиск по всем
строкам и открывает основания обеих сторон. Сводка закрытой области даёт переход
к отдельной точке. Полный HTML включает все строки и основания. CSV общей сверки
использует всю отфильтрованную выборку независимо от открытой страницы.
Общая сверка поддерживает независимые фильтры группы источника и назначения.
Редактор поддерживает те же направления и поиск по ID, политике и сервису.
Представление «Заданные пары» использует только занятые ячейки, а выбор строки
открывает точное требование или закрытую область. Сетка остаётся доступна для
просмотра пересечений. Из выбранной пары, включая пустое пересечение, можно
задать несколько сервисов для текущей области и просмотреть совпадения
и противоречия перед добавлением. ID политики выбирается по сохранённым источникам области
или задаётся вручную. Совпадающий ID требует отдельного выбора источника.
Адреса ресурса можно подтвердить для выбранного источника и площадки из строки
сверки. При совпадении IP в разных сетевых контекстах учитывается точный ключ
источника. Использованные префиксы сохраняются вместе с результатом.
При подтверждённом VRF VLAN ACL состав логических сетей и адресов ресурса
выбирается в этом VRF. Смена VRF между сохранёнными сверками отображается как
изменение области проверки. Одинаковый адрес в другом VRF не доказывает доступ.

Разбор пути открывается из строки общей сверки по сохранённому снимку
коммутатора. Если у строки есть однозначная ревизия, используется она. Для
неоднозначных строк можно выбрать один из сохранённых снимков. Сеансы офиса
и VPN назначаются требованиям выбранной версии из офлайн-снимков разных
сетевых контекстов. Для каждого снимка указывается своё время оценки. Сеанс и
его доказательства хранятся вместе с контекстом и результатом. Одинаковые ID и
адреса в разных VRF разрешаются независимо.

Цепочка связывает обязательные требования через одинаковые группы назначения
и источника соседних участков. Допускается участок с явно указанным пробелом.
Сохранённые сверки разных устройств дают отдельные выводы по участкам, с
привязкой к версии матрицы и происхождению. Проверка рабочего пути требует
отдельных фактов о связи участков и состоянии сети.
Из открытой общей сверки все её участки назначаются из одной сводки. В разборе
наблюдений используется сохранённая ревизия соответствующего участка.

### MATRIX-02. Представление и оценка

Общее ограничение может объединять несколько явно заданных точек проверки с
одинаковыми группами, сервисом и областью. Сводка сохраняет известные лишние
разрешения даже при пробелах в других точках. При сравнении вывод и применимость
каждой политики видны отдельно.

Основное редактирование — таблица требований с карточкой. Дополнительная сетка «группа × группа» фильтруется по сервису/identity; ячейка раскрывает требования, не смешивая разрешённые и запрещённые порты.

Результаты: соответствует в проверенной области, расхождение, недостаточно данных, не регламентировано; отдельно — неприменимость/конфликт требования. Для каждой оценки сохраняются requirement ID/version, ревизии, профиль, evidence и ограничения.

Разделить два режима: сопоставление с заданными условиями правил и проверка фактического пути. Первый не гарантирует reachability. Наличие allow само по себе не подтверждает требование доступности, а отсутствие найденного allow не доказывает запрет. При неподдержанном first-match, identity, NAT, маршрутизации или неполном пути использовать «недостаточно данных» для соответствующего утверждения, сохраняя полезные локальные свидетельства.

Матрица необязательна для базового анализа миссконфигураций. Её отсутствие не блокирует регулярную проверку и не обозначается ошибкой.

## 13. Единый отчёт

### REPORT-01. Структура и воспроизводимость

Один шаблон для всех ролей: область и время → краткая сводка → полнота/ошибки → находки → изменения → решения/комментарии → технические доказательства и ограничения. Отдельные краткий и инженерный виды не обязательны.

Фиксируются run/revision IDs, версии профиля/матрицы/анализатора, область, фильтры, источник данных и дата генерации. Отчёт строится по сохранённым результатам, не запускает анализ повторно и не зависит от текущего состояния дашборда. Пользователь выбирает полный результат или выборку; выборка явно обозначается. Изменение каталога/marks после экспорта не меняет уже созданный файл.

Основной читаемый формат — существующий HTML; JSON сохраняет машинные результаты, CSV — табличную выборку с обозначением ограничений. PDF/DOCX не обещаются этим ТЗ. Экспорт исключает секреты, экранирует имена и исходные фрагменты. Предпросмотр показывает, какие сведения попадут в документ. Маскирование адресов/имён, если вводится, использует последовательные псевдонимы и явно отмечается.

## 14. Архитектура и контракты реализации

### ARCH-01. Разделение ответственности

Domain: факты/условия, идентичность, версии требований и неизменяемые результаты. Application: единый цикл, зависимости заданий, запросы, сравнение, проекции, экспорт. Infrastructure: коллекторы, чтение файлов, persistence, clock/scheduler adapters. Qt: команды, подписка на события, представление. Сервис сценария не импортирует Qt и не требует открытой страницы.

Новые логические сущности: Scope, Source, Run/RunItem, ProfileVersion, AssetIdentity/Binding, MatrixVersion/Requirement, DecisionDependency, Schedule и MapViewState. Это роли данных, не указание создавать дубли существующих классов. Перед реализацией определить повторное использование текущих organization/project/store сущностей и владельца каждого поля.

UI DTO/агрегаты отделены от AnalysisResult, DeviceRevision и AclMap. Агрегация/фильтры карты не меняют evidence и исходную cardinality. Общая сеть строится отдельной проекцией поверх ревизий с provenance; межустройственные ссылки не вставляются в старый локальный контракт TopologyLink.

### ARCH-02. Хранение и совместимость

SQLite остаётся текущим хранилищем. Миграции версионированы, транзакционны, с резервной копией до изменения и отказом от записи при неподдержанной версии. Сбой не оставляет частично активированную схему. Возврат к предыдущей версии выполняется восстановлением совместимой копии; обратная миграция не подразумевается.

Старые projects нельзя автоматически объявлять физическими площадками: требуется явное сопоставление/сохранение legacy-origin. Учитывать существующие org_context/origins/profiles/connections/devices и механизм активации организации, не создавать параллельный независимый каталог. Не терять runs, items, marks, scan provenance, карты и ревизии.

Новые поля читаются из старых данных консервативно: unknown/null, а не известное отсутствие. Исторические результаты не пересчитываются при чтении. Новые версии JSON имеют явную schema_version и поведение при неизвестной версии; совместимость CLI и экспортов документируется. UI-настройки карты не требуют изменения схемы семантического графа, если контракт не меняется.

Потоки используют собственные подключения SQLite и короткие транзакции; поздние события проверяются по run/scope ID. Для больших историй вместо полной повторной десериализации всех запусков нужны выборки, индексы и ограниченные read models.

Компактная облачная история сохраняет ID сборов, счётчики и сведения обо всех наблюдавшихся ресурсах. Карточки, правила и карта читают нужные записи по ID сбора и исходному индексу. Для просмотра и экспорта облачного сбора загружается один выбранный снимок. При недоступной записи интерфейс сообщает о неполноте, а сохранённые ссылки на источники продолжают указывать на их исходную позицию.

### ARCH-03. Подготовка к серверу

Задания и расписания отделены от жизненного цикла виджетов, контекст организации передаётся явно, секреты выдаются через абстракцию хранилища. Это облегчает перенос исполнения, но не означает готовность к многопользовательской работе. REST, PostgreSQL, центральный audit, SSO/RBAC и серверный scheduler проектируются отдельным этапом. Общая SQLite на сетевом диске не предлагается как серверный режим.

## 15. Производительность и качество

### PERF-01. Профили нагрузки

Для будущей приёмки использовать синтетические данные: (A) около 100 устройств со смешанными ролями, два набора по 2000 правил, NGFW 500, 40 VDC суммарно 700; (B) 100 устройств по 2000 правил; (C) каталог более 1000 площадок с ограниченным раскрытым срезом. A повторяет характер нагрузки пользователя, B/C — предлагаемые целевые профили, а не уже достигнутые показатели. Число исторических запусков, максимальные правила одного NGFW и характеристики эталонного ПК требуют фиксации до нагрузочной приёмки.

Таблицы используют ленивую загрузку/виртуализацию; не создавать отдельный QWidget на каждую строку. Фильтрация/сортировка не блокируют UI на полном наборе. Карта обрабатывает ограниченную визуальную проекцию; экспорт больших результатов работает фоном. Отмена/ограничение бюджета вычисления сохраняет partial с объяснением, а не успешный пустой результат.

Предлагаемые измеримые цели после фиксации ПК: визуальное подтверждение команды до 300 мс, первый пригодный к работе экран до 3 с без ожидания полной истории, фильтр загруженной таблицы до 1 с, построение ограниченного вида карты до 2 с. Это проектные бюджеты для согласования и измерения; сроки анализа и лимит памяти не назначаются без baseline. Операции длиннее бюджета переходят в фон с явным статусом, но это не заменяет достижение утверждённых метрик.

### SAFE-01. Достоверность и данные

Неизвестное не равно ANY; ноль findings не равно безопасность; инвентаризация не равна анализу; неполный новый снимок не доказывает исправление или удаление. Пользовательские подписи и решения отделены от фактов. Ключи/пароли не попадают в логи, отчёты и карты; текущий защищённый механизм хранения сохраняется. Диагностика содержит безопасные идентификаторы и причины, а не полный сырой конфиг.

## 16. Критерии приёмки

Критерии ниже — наблюдаемое целевое поведение, не поручение создавать тестовые файлы или запускать локальные проверки. Автоматизация и среда приёмки подчиняются AGENTS; существующие gates выполняются через GitHub Actions после отдельно разрешённой публикации.

| Пороги резкого изменения и давности | Настройки профиля; 30% лишь начальное предложение | Финальную настройку предупреждений |
| Источник состава AD-групп | Пока показывать ссылки/неизвестное членство; коннектор отдельно | Полную identity-оценку, не UI условия |
| Матрица и конфликтующие требования | Не считать конфликт решённым без явного правила | Соответствующие оценки матрицы |
| Полное исследование пути | Отдельная спецификация покрываемых платформ, маршрутов, NAT и runtime-фактов | Сквозную reachability, не карту условий |
| Пропущенный запуск | Один запуск после возобновления, настраиваемо | Окончательное поведение scheduler |
| Производительность и хранение истории | Зафиксировать ПК, объёмы истории, бюджеты памяти/времени; без автоматического удаления | Нагрузочную приёмку и retention |
| Серверная версия | Отдельное архитектурное решение после desktop | Совместную работу и исполнение при выключенном ПК |

Уточнения не блокируют подготовку экранов, режим фокуса, карточки и единый ручной запуск. При реализации нельзя объявлять закрытыми зависимые функции только на основании наличия UI.
