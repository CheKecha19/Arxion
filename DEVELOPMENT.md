# Инструкции разработки и поставки

Основной порядок работы и разрешения — [AGENTS.md](AGENTS.md). Правила безопасности и области сканирования — [SECURITY.md](SECURITY.md). Функциональность — [DOCUMENTATION.md](DOCUMENTATION.md); единственный статус, roadmap и backlog — [PROJECT_STATUS.md](PROJECT_STATUS.md).

## Работа с кодом

- До v1.0 приоритет — код приложения и запрошенные функции. Новые тесты, fixtures и тестовая инфраструктура — только по прямому запросу.
- Проверки по умолчанию выполняются в GitHub Actions. Локальные tests/lint/format/type/harness/security/setup/build/smoke — только по прямому запросу.
- Для небольших задач: релевантные файлы, изменение, обзор diff, краткий результат.
- Для крупных задач: план и прогресс в PROJECT_STATUS.md, прямая проверка downstream-потребителей, JSON/SQLite, Qt и runtime imports. Не создавать новые status/backlog/TASK-файлы.
- Для существенных работ записывать базовый SHA, что просмотрено, CI/сборочные результаты и непроверенные ограничения в журнал PROJECT_STATUS.md. Исторические журналы находятся в архиве.
- Работать в текущем checkout; без worktree по собственной инициативе. Делегирование разрешено согласно AGENTS.
- Предпочитать Python/PySide6, uv, Ruff и mypy; pytest/Hypothesis — в пределах политики тестирования.
- Domain не зависит от UI/адаптеров. Парсеры возвращают модель и диагностику; checks не выполняют I/O. Application связывает сценарии, UI представляет результаты.
- Сохранять unknown/unsupported/partial, provenance и исходные доказательства. Не подменять неизвестное ANY и не обновлять goldens ради прохождения проверки.
- Изменения JSON/SQLite документировать в DOCUMENTATION.md: совместимость чтения, миграция и ограничения. Не создавать отдельные документы миграции для каждой задачи.
- Документация, пользовательские пояснения и комментарии — по умолчанию на русском; код, API и Git-заголовки — на английском. Комментарии объясняют причину, не пересказывают код.
- Клиентские конфигурации и секреты не помещать в Git/логи; данные для разработки только синтетические.
- Commit/push, удаление, публикация и реальные облачные аккаунты требуют разрешения пользователя.

## CI и карты проекта

Workflow `.github/workflows/harness.yml`: Windows jobs для карт/context/impact/architecture, quality, test, smoke, package и security. Триггеры — PR, push в main и manual dispatch. Каждый job сохраняет логи и артефакты отдельно.

Доступные команды harness: setup, context, impact, maps, architecture, quality, test, smoke, package, security, all. Наличие команды не разрешает локальный запуск. Даже анализ context/impact/maps по умолчанию выполняется в CI. Анализ импортов статический, Qt-сигналы и runtime-потребители требуют исходниковой сверки.

Артефакт `project-maps`: структура пакетов, зависимости, `package-*.md/.mmd`, README и JSON с SHA. Это исходники Mermaid, не готовые изображения. Скачивать из GitHub Actions и открывать в редакторе с Mermaid.

Пропущенная/нулевая/не выполненная проверка не считается успешной. Linux/offscreen и успешная упаковка сами по себе не подтверждают нативную Windows-готовность.

## Политика Git и выпусков

### Именование коммитов, тегов и релизов

Правила действуют для последующих изменений. Исторические коммиты, теги и
релизы не переименовываются. Это соглашение проекта; автоматическая проверка
формата пока не настроена.

## Коммиты

Формат заголовка: `<type>[(scope)][!]: <description>`.
Тип и необязательная область — на английском в нижнем регистре; описание —
краткое, на английском, с глагола, без точки в конце. Один коммит описывает
одно связное изменение. Версия в обычном коммите не нужна.

| Тип | Назначение | Пример |
| --- | --- | --- |
| `feat` | Новая возможность | `feat(analysis): add ACL attachment checks` |
| `fix` | Исправление ошибки | `fix(desktop): restore integration settings access` |
| `docs` | Документация | `docs: define commit and release naming` |
| `refactor` | Изменение структуры без изменения поведения | `refactor(storage): simplify snapshot loading` |
| `perf` | Производительность | `perf(desktop): defer workspace loading` |
| `build` | Зависимости и сборка | `build: unify Windows distribution names` |
| `ci` | GitHub Actions | `ci: update Windows workflow configuration` |
| `test` | Явно запрошенные изменения тестов | `test(analysis): cover empty configurations` |
| `chore` | Прочее обслуживание | `chore: update repository metadata` |
| `release` | Подготовка выпуска | `release: prepare v0.4.0` |

Область уточняет компонент, например `desktop`, `cli`, `analysis`, `storage`.
Для несовместимого изменения ставится `!`, например
`feat(storage)!: change snapshot format`; в теле коммита добавляется
`BREAKING CHANGE: ...` с описанием последствий и перехода.
Заголовки PR следуют тому же формату, чтобы сохранять его при squash merge.
Автоматические merge/revert-коммиты могут сохранять стандартные заголовки Git.
Тип `test` не отменяет ограничений AGENTS.md на создание тестов.

## Версии и имена выпусков

Источник версии — `[project].version` в `pyproject.toml`. Рабочий формат:
`MAJOR.MINOR.PATCH[.REVISION]`. Четвёртый компонент — счётчик документальных
и служебных изменений, не влияющих на функции, поведение и контракты приложения.
Это не build metadata, не prerelease и не общее число коммитов.

| Изменение | Как повышается версия | Пример |
| --- | --- | --- |
| Новые функции до v1.0 | MINOR, сброс PATCH и REVISION | `0.3.2 → 0.4.0` |
| Исправление поведения | PATCH, сброс REVISION | `0.4.0.3 → 0.4.1` |
| Только документация/служебные правки | REVISION | `0.4.0 → 0.4.0.1 → 0.4.0.2` |
| Совместимые новые функции после v1.0 | MINOR, сброс младших | `1.2.3.4 → 1.3.0` |
| Несовместимость после v1.0 | MAJOR, сброс младших | `1.2.3.4 → 2.0.0` |

- У нового функционального выпуска REVISION равен нулю и не записывается:
  `0.4.0`, а не `0.4.0.0`. Первый последующий служебный checkpoint — `0.4.0.1`.
- REVISION повышается один раз на согласованную группу документальных/служебных
  изменений при подготовке её к commit/push. Промежуточные правки этой группы,
  сам push и повторная сборка не повышают его ещё раз.
- В смешанном изменении выбирается старший применимый компонент. Документация
  нового функционального выпуска уже входит в MINOR и не добавляет `.1`.
- Изменения CI/упаковки/зависимостей не считаются автоматически служебными:
  если меняется поведение поставляемого приложения или исправляется баг,
  применяются PATCH/MINOR/MAJOR. Несовместимость не маскируется под PATCH.
- До 1.0 новые возможности и несовместимость повышают MINOR; решение о 1.0
  принимается отдельно. Начиная с 1.0 действуют MAJOR/MINOR по таблице.
- MAJOR/MINOR выпускаются с тегом `vMAJOR.MINOR.PATCH` и GitHub Release
  `FirewallComplience vMAJOR.MINOR.PATCH`; коммит `release: prepare v0.4.0`.
- PATCH — коммит `fix(scope): description`, без отдельного тега/GitHub Release.
  REVISION — соответствующий `docs:`, `chore:` или `ci:` коммит, также без
  отдельного тега/GitHub Release. Эти изменения входят в следующий основной выпуск.
- Версии во всех трёх местах согласуются даже для REVISION: `pyproject.toml`,
  `src/firewall_compliance/__init__.py`, запись своего пакета в `uv.lock`.
  Версии зависимостей не изменяются из-за повышения версии приложения.
- Дистрибутив использует буквальную версию: `FirewallComplience_v0.4.0.2`.
  Формат допускает четвёртый числовой компонент; это соглашение проекта поверх
  Python-версии, а не трёхкомпонентный SemVer.
- Исторические коммиты, теги и релизы не переименовываются. Не переиспользовать
  опубликованный номер. Следующий номер не назначается одним примером в документе.
- Предварительные выпуски: тег `v0.4.0-alpha.1`/`beta.1`/`rc.1`, Python-метаданные
  `0.4.0a1`/`0.4.0b1`/`0.4.0rc1`, GitHub Release отмечается pre-release.
  REVISION не используется как счётчик предварительных выпусков.
- Commit, push, повышение версии и сборка не выполняются автоматически скриптом.
  Публикация/тег/релиз требуют разрешения пользователя согласно AGENTS.md.

## Документация и описание изменений

- В каждом мажорном обновлении документация пересобирается целиком под
  выпускаемую версию: README, DOCUMENTATION.md, инструкции установки
  и сборки, описание функционала, CLI, форматов данных и архитектуры.
  Содержание сверяется с текущим приложением; устаревшие инструкции и примеры
  обновляются, ссылки и навигация согласуются. Исторические заметки о выпусках
  сохраняются как история. В заметках релиза указываются основные изменения
  и необходимые действия при переходе.
- В каждом минорном обновлении подробно описывается добавленный функционал
  в заметках релиза и соответствующих разделах документации: назначение,
  где он доступен, как им пользоваться, входные данные, результат, ограничения
  и примеры. Описание должно позволять пользователю применить новую возможность.
- Для фиксов в теле коммита приводится краткий ненумерованный список
  исправленных багов. Каждый пункт имеет формат `* краткое название - суть бага`.
  Заголовок коммита сохраняет формат `fix(scope): description`. При включении
  фиксов в следующий релиз этот же формат используется в разделе исправлений
  его заметок; отдельный релиз для фиксов не создаётся.

Пример тела коммита с фиксами:

```text
* Настройки интеграции - окно не открывалось из меню проекта
* Пустой список ACL - приложение завершалось при открытии карты
```

Пересборка документации не отменяет правила AGENTS.md: автоматические проверки
и генерация через сборочные инструменты выполняются в GitHub Actions;
локальный запуск требует прямого запроса пользователя.

## Подготовка и публикация

Для документальных/служебных checkpoint повысить REVISION, согласовать три файла версии и обновить журнал PROJECT_STATUS.md. Тег и GitHub Release не создавать.

Для фиксов повысить PATCH и согласовать `pyproject.toml`,
`src/firewall_compliance/__init__.py` (`__version__`) и запись собственного
пакета в `uv.lock` до сборки и коммита. Добавить список исправлений в тело
коммита `fix:`. Тег и GitHub Release не создавать. Соблюдать ограничения
AGENTS.md на запуск инструментов и публикацию изменений.

Для мажорного или минорного релиза:

1. Определить состав выпуска и номер относительно текущей версии приложения
   и истории версий, включая PATCH/REVISION-коммиты без релиза. Проверить также удалённые
   теги и GitHub Releases: локальный список тегов может быть неполным.
   Не переиспользовать уже опубликованный номер.
2. При подготовке версии согласовать `pyproject.toml`,
   `src/firewall_compliance/__init__.py` (`__version__`) и запись собственного
   пакета в `uv.lock`. Соблюдать ограничения AGENTS.md на локальный запуск
   инструментов. Подготовить документацию по правилам выше для мажорного
   или минорного обновления.
3. Подготовить заметки: новые возможности, исправления, несовместимости и
   миграция, известные ограничения, фактические результаты CI и доступные
   файлы. Соблюдать требования выше к подробности описания функционала
   и формату списка фиксов. Не выдавать пропущенные или незапущенные проверки
   за успешные.
4. После разрешённого commit/push проверить результаты GitHub Actions именно
   для выпускаемого SHA. Ошибки устранить; отсутствие результата явно указать.
   Публиковать выпуск после успешных применимых проверок; исключение требует
   явного решения пользователя. Локальные проверки и сборки — только по запросу.
5. Создать аннотированный тег на конкретном проверенном коммите подготовки
   выпуска. Один тег соответствует одному GitHub Release в репозитории.
   Подготовить draft релиза, приложить разрешённые артефакты, затем публиковать
   в пределах разрешения пользователя.

Windows-поставка следует [DEVELOPMENT.md](DEVELOPMENT.md):
вся папка приложения, без автоматического ZIP и отдельных feature-сборок.
Один EXE из этой папки не является самостоятельным дистрибутивом.
Автоматические архивы исходников GitHub не являются готовой Windows-сборкой.

Опубликованный тег не перемещаем, не удаляем и не используем повторно;
опубликованные бинарные файлы не подменяем. Исправления кода или поставки
сохраняются коммитами и входят в следующий мажорный или минорный выпуск
с новым номером и тегом. Исправить текст заметок без изменения содержимого
выпуска допустимо. Перезапись локальной папки сборки, разрешённая правилами
Windows, не даёт разрешения подменять опубликованный выпуск.

Git технически позволяет заменить тег, но это запрещено данным соглашением.
GitHub позволяет выбрать существующий тег либо создать новый при создании
релиза; заранее создавать тег технически необязательно.

Соглашение не разрешает commit, push, создание тегов или публикацию само по
себе: эти действия выполняются только в пределах запроса пользователя.

Справка: [Git tag](https://git-scm.com/docs/git-tag),
[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

# Правила сборки Windows-дистрибутива

Действуют с 29.10.2026 для всех последующих сборок. Заменяют прежние инструкции
об отдельных CLI/feature-поставках и автоматическом ZIP.

- Собирается весь текущий проект из существующего checkout, со всеми прикладными
  модулями и данными пакета. Отдельные сборки CLI, платформ и фич не выпускаются.
  Инструменты разработки не являются частью поставки.
- Папка результата: `dist/FirewallComplience_v<версия>`. Написание
  `FirewallComplience` фиксировано. Версия автоматически берётся из
  `[project].version` в `pyproject.toml`.
- EXE: `FirewallComplience_v<версия>.exe` внутри этой папки. Текущий пример:
  `dist/FirewallComplience_v0.3.2/FirewallComplience_v0.3.2.exe`.
- Повторная сборка той же версии перезаписывает существующую папку и EXE.
  Суффиксы фич, дат, копий, `ArubaUpdate`, `ArxionCLI` и произвольные варианты
  имени запрещены. Перед перезаписью приложение нужно закрыть.
- ZIP и другие архивы автоматически не создаются. Архивирование — только по
  отдельному прямому запросу пользователя.
- Переносится вся папка, включая `_internal` и `README.txt`; один EXE без
  зависимостей не является полной поставкой.
- Старые дистрибутивы и архивы не удаляются без отдельного разрешения пользователя.
- Сборка не запускает тесты, smoke или готовый EXE. Проверки выполняются отдельно
  в соответствии с AGENTS.md и прямыми указаниями пользователя.

Штатная команда в подготовленном Windows-окружении `.venv`:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build_desktop.ps1
```

`-Console` меняет только видимость консоли, сохраняя папку и имя.
`-Variant` и `-ArubaUpdate` больше не поддерживаются.
Старый `scripts/build_cli.ps1` перенаправляет на полную сборку, отдельный CLI EXE
не создаётся. CLI из исходников доступен через `firewall-compliance`.
