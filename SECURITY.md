# Область сканирования безопасности

Этот документ задаёт список исключений для сканирований исходного кода проекта.
Перед новым запуском список должен быть прочитан и учтён в настройках области
проверки. Пути указаны относительно корня проекта; `/` используется как разделитель.
Шаблоны ниже описывают желаемые исключения, а не универсальный формат конфигурации
сканера: их необходимо перевести в поддерживаемый конкретным инструментом формат.

## Что проверять

- `src/firewall_compliance/**` — собственный код приложения, кроме кэшей.
- `scripts/qt_launcher.py` — точка входа Windows-сборки.
- `scripts/build_desktop.ps1` и `FirewallCompliance.spec` — сборка и упаковка.
- `Start-Desktop.cmd` — запуск приложения.
- `pyproject.toml` и `uv.lock` — настройки и зависимости. Проверка зависимостей
  выполняется по этим файлам, без обхода установленного окружения.
- `README.md`, этот документ и `DOCUMENTATION.md`, `DEVELOPMENT.md` и `PROJECT_STATUS.md` — контекст
  архитектуры и требований, без обязательного построчного аудита всех документов.
  Базовые требования безопасности находятся в `разделе «Базовые требования» ниже`.

Новые собственные модули и рабочие ресурсы приложения включаются в проверку,
если они не относятся к явно указанным ниже исключениям.

## Границы исключений

- `src/firewall_compliance/interfaces/desktop/packaged_smoke.py` остаётся в области
  проверки: он вызывается из `scripts/qt_launcher.py` по аргументу `--self-test`
  и входит в поставляемое приложение.
- Расширения `.py`, `.json`, `.txt`, `.conf`, `.cfg`, `.html` и подобные сами по себе
  не являются основанием для исключения. Рабочие ресурсы и настройки могут влиять
  на безопасность приложения.
- Исключение временных файлов и экспортов не исключает проверку кода, который
  создаёт, читает, защищает или удаляет эти файлы.
- Исключение тестов не исключает проверку соответствующих функций приложения.
- Этот список относится к анализу исходного кода. Он не утверждает безопасность
  исключённых файлов и не задаёт исключения для отдельно запрошенной проверки
  секретов, зависимостей или безопасности готовой поставки.

## Применение при запуске

1. До запуска определить целевую область и применить исключения средствами сканера.
2. Передать этот документ как контекст проверки, если инструмент это поддерживает.
3. Если инструмент не поддерживает необходимые исключения, явно указать это
   ограничение; наличие `SECURITY.md` само по себе не гарантирует фильтрацию файлов.
4. В результатах указывать фактически проверенные пути, применённые исключения
   и ограничения покрытия.
5. Уже запущенная проверка сохраняет свою исходную область. Этот документ не меняет
   область текущего скана автоматически.

## Статус

Этот документ задаёт минимальный временный baseline. Он не заменяет будущие обязательные архитектурные и кибербезопасностные требования; после их получения документ будет сопоставлен с ними и обновлён.

Требования ниже являются критериями реализации и выпуска, а не утверждением о завершении всех защитных механизмов. До согласования обязательных требований используются только synthetic fixtures; готовность обработки реальных конфигураций заказчика не заявляется.

## Данные

- Конфигурации, отчёты и findings считаются чувствительными данными.
- Обработка выполняется локально по умолчанию.
- Реальные конфигурации, пароли, ключи, токены и адресные планы не включаются в Git, fixtures, логи, Docker images или диагностические дампы.
- Временные файлы и экспортированные отчёты создаются только в явно указанном каталоге пользователя или проекта.
- JSON в stdout является отчётом, а не безопасным логом: он может содержать нормализованные адреса, названия объектов, описания правил и evidence. Перенаправленный stdout и все копии отчёта защищаются как конфигурационные данные.
- В desktop UI сохранённый JSON, скопированное evidence и явно открытый исходный
  фрагмент также считаются конфигурационными данными. Source preview проверяет
  captured snapshot и не открывает произвольные пути из evidence; это не механизм
  маскирования секретов. Автоматическое добавление исходного файла целиком в отчёт отсутствует.

## Выполнение

- Приложение не устанавливает зависимости и не выполняет произвольные команды автоматически во время анализа.
- Внешние соединения отсутствуют по умолчанию и требуют явной настройки.
- Процесс запускается с минимально необходимыми правами файловой системы.
- Ошибки не должны раскрывать содержимое конфигурации в консоли или логах.
- Диагностические сообщения и исключения требуют отдельной проверки на утечки паролей, ключей и сырых фрагментов конфигурации. Наличие source mapping не разрешает вывод секретов; готовый механизм их редактирования/маскирования пока не заявляется.

## Поставка

- Зависимости фиксируются и регулярно проверяются на известные уязвимости.
- Релизный артефакт сопровождается версией, хешем и SBOM.
- Если выпускается Docker image, он строится из минимального базового образа, проходит image scan и не содержит секретов или данных заказчика. Это не обязательная часть первой Windows-поставки.

## Аудируемость

- Для каждого анализа сохраняются идентификатор запуска, хеш входного файла, версии приложения/парсера/checks, время и итоговый статус.
- Хеш конфигурации сохраняется в ревизии; общий AnalysisResult хранит входы и provenance, SQLite сохраняет результаты и историю решений по находкам. Это не централизованный журнал всех действий. Полное соответствие SR-006 оценивается по контракту AnalysisResult и конкретной операции, а не по наличию хеша в верхнем FirewallAssuranceResult.
- Изменение статуса finding в будущей серверной версии фиксируется в audit log.
