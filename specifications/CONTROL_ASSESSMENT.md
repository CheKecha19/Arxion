# Технические свидетельства для внутренних контролей

Срез реализует версионируемые организационные требования и many-to-many
сопоставления поверх сохранённого `AnalysisResult`. Используется выбранный
пользователем внутренний baseline. Каталог не содержит непроверенных
сопоставлений с NIST, CIS или PCI DSS и не заявляет сертификацию.

## Контракты и область

`domain/controls.py`: `ControlCatalogue`, `CheckControlMapping`,
`OrganizationControlProfile`, `ControlRequirement`, `ControlException`,
`ControlEvaluation`, `ControlCoverage`. Обычное создание, JSON и `model_copy`
валидируют входы и глубоко замораживают вложенные значения. Неизвестная версия
schema, дублирующиеся IDs/связи, неверные ссылки и неоднозначные параметры
отвергаются. Домен не импортирует application, Qt, SQLite или файловые читатели.

`application/control_assessment.py` предоставляет:

- `internal_control_catalogue()`: пять узких внутренних технических частей:
  широкие разрешающие условия, журналирование, комментарии, запрещённые
  организацией сервисы, административные источники. Организация явно выбирает
  применимые требования; наличие каталога не делает все части обязательными.
- `assess_controls(source, profile, catalogue, assessed_at=...)`: чистый расчёт
  без файлов, сети, текущих настроек проекта и инвентаря ресурсов.
- `ControlAssessment`: полный точный source `AnalysisResult`, профиль, каталог,
  дата, выводы и охват. Выводы и счётчики воспроизводятся при загрузке; подмена
  успешного исхода или охвата отвергается. Это проверка внутренней согласованности,
  а не электронная подпись, проверка авторства или удостоверение утверждения.
- `export_control_assessment_json/csv/html`: строки для выбранного файла.

Профиль содержит организацию, ID/версию, явную ссылку на область, применимость
каждого требования с обоснованием, параметры и исключения. `component_ids=None`
означает все policy-компоненты и неуспешные policy attempts именно сохранённого
пакета. Это не все устройства проекта. Явная пустая область запрещена; неизвестный
или не-policy компонент не становится успешной оценкой.

Параметры сопоставляются с точными `PolicyAnalysisOptions`: require_logging,
require_comments, management_profile, exposure_profile. Несовпадение даёт
недостаток свидетельств; оценка не перезапускает анализ с другими настройками.
Отключённое журналирование/комментарии в исходном анализе не доказывают выполнение
контроля, который их требует. Для профилей используется точное JSON-сравнение.

Каждая связь содержит отдельный ID, check_id и поддержанные check_versions,
источник, редакцию, исходный ID контроля, обоснование, покрываемую часть и
ограничения. Несколько checks могут требоваться одному контролю; один check
может поддерживать несколько контролей. Сопоставления внутреннего каталога
связаны с принципами A-06/S-07 матрицы требований только в части сохранения
технического свидетельства и unknown. Они не доказывают выполнение всего
архитектурного или защитного требования A-06/S-07.

## Исходы и охват

Четыре исхода явно различаются:

| Исход | Основание |
| --- | --- |
| technical_violation | Подтверждённая finding сопоставленной версии check в согласованных параметрах |
| no_violation_in_examined_scope | Все требуемые checks выполнены полностью, в согласованных параметрах, без findings и ограничений |
| insufficient_evidence | Нет результата/check/mapping, версия не сопоставлена, параметры не совпадают, либо данные partial/unknown/failed/not_executed |
| not_applicable | Только явная неприменимость в профиле с обоснованием |

Техническое нарушение может быть доказано в частично проверенной области:
тогда finding сохраняется, а охват не считается полным. Runtime not_applicable
отдельного check сам по себе не делает организационное требование неприменимым.
Состояния complete/partial/not_applicable/not_executed/missing каждого check
видны отдельно. Полный охват считается по фактически достаточным check
evaluations, а не по числу ресурсов или отсутствию findings. Требование без
mapping остаётся недостаточно оценённым и не исчезает из числа требований.

Существующие checks administrative/dangerous services исследуют заданные
условия ALLOW; они не доказывают эффективный first-match путь или доступность
сервиса. Эти границы остаются в каталоге, исходном отчёте и assessment.
Непроверенные организационные процедуры не получают автоматического PASS.

## Исключения и история

Исключение ссылается на точные control/component/finding, содержит причину,
указанного утвердившего, aware approved_at/expires_at. Неизвестная finding,
чужой scope или finding несвязанного check отвергаются. Активность определяется
`approved_at <= assessed_at < expires_at`; истёкшие и будущие исключения
сохраняются в профиле, но не действуют. Подпись/роль утвердившего этим локальным
контрактом не проверяются — это отдельная задача RBAC/audit.

Активное исключение сохраняется как отдельная ссылка в evidence и не удаляет
finding либо технический вывод. Решения пользователя accepted_risk,
false_positive и прочие остаются в исходном AnalysisResult отдельно; они не
подменяются автоматически утверждённым исключением. Изменение текущего профиля
не переписывает исторический snapshot; новый assessment сохраняется отдельно.

## CLI

```text
ArxionCLI controls catalogue --output catalogue.json
ArxionCLI controls profile-template --output profile.json --organization Org \
  --scope-reference "Выбранные policy-компоненты" --profile-id org-policy \
  --version 1 --control TECH-ADMIN-SOURCES --justification "Выбранная политика"
ArxionCLI controls assess analysis.json --profile profile.json --output assessment.json
ArxionCLI controls export assessment.json --output assessment.html --format html
ArxionCLI controls export assessment.json --output assessment.csv --format csv
```

`--catalogue` позволяет явно выбрать сохранённый каталог; по умолчанию внутренний.
`--assessed-at` задаёт воспроизводимую aware дату не раньше завершения анализа.
Создание шаблона не означает утверждение за организацию: применимость,
обоснование, параметры и scope задаёт вызывающий. `--not-applicable` требует
того же явного обоснования. Внешние сопоставления могут быть введены только
как отдельно проверенные и версионированные данные; встроенных NIST/CIS нет.

Входные UTF-8 JSON ограничены 64 МиБ; catalogue до 256 контролей/1024 mappings
и 1 МиБ. Профиль до 256 требований, 1000 явных компонентов и 4096 исключений;
параметры одного требования до 128 КиБ. Оценка ограничена 10000 сочетаний
control/component и 100000 сочетаний mapping/component. Превышение вызывает
явный отказ; частично созданный успешный результат не возвращается.

Выход не может совпасть с любым выбранным входом, включая жёсткие ссылки.
Ошибки CLI не печатают входные документы. Экспорт historical assessment не
читает исходные конфигурации, проекты или текущие профили. JSON включает полные
снимки и может содержать чувствительные нормализованные данные; HTML экранирует
текст, CSV защищает ячейки от формул. Экспорт не является обезличиванием.

## Интеграционные границы и приёмка

В «Отчётах» подключена вкладка «Технические контроли». Сначала выбирается
сохранённый общий результат, затем явно загружается профиль организации и
при необходимости другой каталог. Новая оценка выполняется worker и сохраняется
в отдельной immutable checksummed таблице control_assessments. Источник должен
точно соответствовать ранее сохранённому AnalysisResult того же проекта.
Изменение текущего профиля не переписывает старые оценки.

История открывается после перезапуска без исходных конфигураций и текущего
профиля; четыре исхода, охват и ограничения остаются видимыми. Экспорты
JSON/CSV/HTML используют сохранённый снимок. Смена проекта и отмена исключают
устаревшую доставку; уже начатый commit может завершиться в исходном проекте.
Таблица переносится с полной SQLite backup; semantic inspector v1 ещё не
включает её в свой старый каталог.

Отдельный набор storage/UI содержит30 тестов, core/CLI —57. Совместная
Qt-приёмка после добавления вкладки метаданных правил ещё диагностируется:
успешные assertions не заменяют корректное завершение нативного процесса.
Это не завершение всего COMPLIANCE-001 и не оценка полного внешнего стандарта.

`harness/tests/test_control_assessment.py` и `test_control_cli.py` проверяют
четыре исхода, real checks/replay, неизвестность, partial/not_executed,
параметры, many-to-many, исключения/сроки, независимые решения findings,
freeze/history, tampering, JSON/CSV/HTML, UTF-8, лимит входа и hardlink guards.
Данные только authored synthetic; реальные облачные аккаунты не используются.
