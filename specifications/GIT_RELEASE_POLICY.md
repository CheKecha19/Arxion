# Именование коммитов, тегов и релизов

Правила действуют для последующих изменений. Исторические коммиты, теги и
релизы не переименовываются. Это соглашение проекта; автоматическая проверка
формата пока не настроена.

## Коммиты

Формат заголовка: `<type>[(scope)][!]: <description>`.
Тип и необязательная область — на английском в нижнем регистре; описание —
краткое, на английском, с глагола, без точки в конце. Один коммит описывает
одно связное изменение. Версия в обычном коммите не нужна.

| Тип | Назначение | Пример |
| --- | --- | --- |
| `feat` | Новая возможность | `feat(analysis): add ACL attachment checks` |
| `fix` | Исправление ошибки | `fix(desktop): restore integration settings access` |
| `docs` | Документация | `docs: define commit and release naming` |
| `refactor` | Изменение структуры без изменения поведения | `refactor(storage): simplify snapshot loading` |
| `perf` | Производительность | `perf(desktop): defer workspace loading` |
| `build` | Зависимости и сборка | `build: unify Windows distribution names` |
| `ci` | GitHub Actions | `ci: update Windows workflow configuration` |
| `test` | Явно запрошенные изменения тестов | `test(analysis): cover empty configurations` |
| `chore` | Прочее обслуживание | `chore: update repository metadata` |
| `release` | Подготовка выпуска | `release: prepare v0.4.0` |

Область уточняет компонент, например `desktop`, `cli`, `analysis`, `storage`.
Для несовместимого изменения ставится `!`, например
`feat(storage)!: change snapshot format`; в теле коммита добавляется
`BREAKING CHANGE: ...` с описанием последствий и перехода.
Заголовки PR следуют тому же формату, чтобы сохранять его при squash merge.
Автоматические merge/revert-коммиты могут сохранять стандартные заголовки Git.
Тип `test` не отменяет ограничений AGENTS.md на создание тестов.

## Версии и имена выпусков

Источник версии — `[project].version` в `pyproject.toml`.

| Объект | Формат | Пример |
| --- | --- | --- |
| Версия приложения | `MAJOR.MINOR.PATCH` | `0.4.0` |
| Тег Git | `vMAJOR.MINOR.PATCH` | `v0.4.0` |
| Название GitHub Release | `FirewallComplience vMAJOR.MINOR.PATCH` | `FirewallComplience v0.4.0` |
| Коммит подготовки | `release: prepare vMAJOR.MINOR.PATCH` | `release: prepare v0.4.0` |

Написание `FirewallComplience` согласовано с Windows-дистрибутивом.
Все числа обязательны: новые теги `v0.4`, даты и названия фич вместо версии
не используются. Примеры не назначают следующий выпуск автоматически.

- Мажорные и минорные изменения оформляются выпуском: коммит подготовки,
  новый тег и GitHub Release. Исправления оформляются только коммитами `fix:`
  (с необязательной областью) с повышением PATCH-версии приложения
  (`0.3.2 → 0.3.3`), без отдельного тега и GitHub Release. Это правило
  действует как до, так и после `1.0.0`. Фиксы входят в следующий мажорный
  или минорный релиз и перечисляются в его заметках. Отдельные GitHub Releases
  для PATCH-версий не создаются.
- До `1.0.0`: новые возможности или несовместимые изменения увеличивают
  MINOR со сбросом PATCH (`0.3.2 → 0.4.0`). Несовместимость явно описывается
  в заметках. `1.0.0` выпускается по отдельному решению о готовности продукта.
- Начиная с `1.0.0`: совместимые возможности увеличивают MINOR,
  несовместимые изменения — MAJOR. При увеличении старшего компонента
  младшие сбрасываются в ноль. Учитываются CLI, форматы JSON, SQLite,
  импорт/экспорт и другие пользовательские контракты.
  Исправление, нарушающее совместимость, также следует правилу несовместимых
  изменений, а не правилу обычного фикса. Компонент PATCH сохраняется в формате
  версии; в новых мажорных и минорных выпусках он равен нулю.
- Несколько коммитов могут входить в один выпуск; выбирается наибольший
  необходимый уровень изменения. Одна согласованная группа фиксов получает
  одно повышение PATCH; промежуточные коммиты той же группы не требуют
  повторного повышения. Документационные и служебные коммиты без изменения
  приложения не требуют новой версии. Сам по себе push номер не меняет.
- Повторная сборка того же кода сохраняет версию и перезаписывает локальную
  папку согласно правилам Windows-поставки. Если сборка включает новые фиксы,
  PATCH повышается до сборки, чтобы исправленное приложение имело новый номер.
  Commit, push и скрипт сборки автоматически версию не повышают: её изменение
  является частью подготовки соответствующего изменения приложения.
- Предварительные теги: `v0.4.0-alpha.1`, `v0.4.0-beta.1`, `v0.4.0-rc.1`.
  Такой GitHub Release отмечается как pre-release. В Python-метаданных им
  соответствуют `0.4.0a1`, `0.4.0b1`, `0.4.0rc1`; дистрибутив использует
  буквальную версию из `pyproject.toml`. Это явное соответствие форматов,
  а не разные версии. Статус серии `0.x` сам по себе не требует суффикса.

## Документация и описание изменений

- В каждом мажорном обновлении документация пересобирается целиком под
  выпускаемую версию: README, руководство пользователя, инструкции установки
  и сборки, описание функционала, CLI, форматов данных и архитектуры.
  Содержание сверяется с текущим приложением; устаревшие инструкции и примеры
  обновляются, ссылки и навигация согласуются. Исторические заметки о выпусках
  сохраняются как история. В заметках релиза указываются основные изменения
  и необходимые действия при переходе.
- В каждом минорном обновлении подробно описывается добавленный функционал
  в заметках релиза и соответствующих разделах документации: назначение,
  где он доступен, как им пользоваться, входные данные, результат, ограничения
  и примеры. Описание должно позволять пользователю применить новую возможность.
- Для фиксов в теле коммита приводится краткий ненумерованный список
  исправленных багов. Каждый пункт имеет формат `* краткое название - суть бага`.
  Заголовок коммита сохраняет формат `fix(scope): description`. При включении
  фиксов в следующий релиз этот же формат используется в разделе исправлений
  его заметок; отдельный релиз для фиксов не создаётся.

Пример тела коммита с фиксами:

```text
* Настройки интеграции - окно не открывалось из меню проекта
* Пустой список ACL - приложение завершалось при открытии карты
```

Пересборка документации не отменяет правила AGENTS.md: автоматические проверки
и генерация через сборочные инструменты выполняются в GitHub Actions;
локальный запуск требует прямого запроса пользователя.

## Подготовка и публикация

Для фиксов повысить PATCH и согласовать `pyproject.toml`,
`src/firewall_compliance/__init__.py` (`__version__`) и запись собственного
пакета в `uv.lock` до сборки и коммита. Добавить список исправлений в тело
коммита `fix:`. Тег и GitHub Release не создавать. Соблюдать ограничения
AGENTS.md на запуск инструментов и публикацию изменений.

Для мажорного или минорного релиза:

1. Определить состав выпуска и номер относительно текущей версии приложения
   и истории версий, включая PATCH-коммиты без релиза. Проверить также удалённые
   теги и GitHub Releases: локальный список тегов может быть неполным.
   Не переиспользовать уже опубликованный номер.
2. При подготовке версии согласовать `pyproject.toml`,
   `src/firewall_compliance/__init__.py` (`__version__`) и запись собственного
   пакета в `uv.lock`. Соблюдать ограничения AGENTS.md на локальный запуск
   инструментов. Подготовить документацию по правилам выше для мажорного
   или минорного обновления.
3. Подготовить заметки: новые возможности, исправления, несовместимости и
   миграция, известные ограничения, фактические результаты CI и доступные
   файлы. Соблюдать требования выше к подробности описания функционала
   и формату списка фиксов. Не выдавать пропущенные или незапущенные проверки
   за успешные.
4. После разрешённого commit/push проверить результаты GitHub Actions именно
   для выпускаемого SHA. Ошибки устранить; отсутствие результата явно указать.
   Публиковать выпуск после успешных применимых проверок; исключение требует
   явного решения пользователя. Локальные проверки и сборки — только по запросу.
5. Создать аннотированный тег на конкретном проверенном коммите подготовки
   выпуска. Один тег соответствует одному GitHub Release в репозитории.
   Подготовить draft релиза, приложить разрешённые артефакты, затем публиковать
   в пределах разрешения пользователя.

Windows-поставка следует [WINDOWS_DISTRIBUTION.md](WINDOWS_DISTRIBUTION.md):
вся папка приложения, без автоматического ZIP и отдельных feature-сборок.
Один EXE из этой папки не является самостоятельным дистрибутивом.
Автоматические архивы исходников GitHub не являются готовой Windows-сборкой.

Опубликованный тег не перемещаем, не удаляем и не используем повторно;
опубликованные бинарные файлы не подменяем. Исправления кода или поставки
сохраняются коммитами и входят в следующий мажорный или минорный выпуск
с новым номером и тегом. Исправить текст заметок без изменения содержимого
выпуска допустимо. Перезапись локальной папки сборки, разрешённая правилами
Windows, не даёт разрешения подменять опубликованный выпуск.

Git технически позволяет заменить тег, но это запрещено данным соглашением.
GitHub позволяет выбрать существующий тег либо создать новый при создании
релиза; заранее создавать тег технически необязательно.

Соглашение не разрешает commit, push, создание тегов или публикацию само по
себе: эти действия выполняются только в пределах запроса пользователя.

Справка: [Git tag](https://git-scm.com/docs/git-tag),
[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).
