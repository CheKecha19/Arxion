# Cloud.ru VMware: подключение и сканирования

Реализован сбор конфигурации VMware Cloud Director через API. В настройках
Cloud.ru есть отдельные подключения VMware, Advanced и Evolution.
Для Advanced и Evolution см. [руководство](CLOUD_RU_PUBLIC.md).
Для каждого локального проекта хранится одно подключение VMware.

## Что заполнить

| Поле | Где взять |
| --- | --- |
| Адрес площадки | Скопируйте адрес из браузера: `https://<площадка>` или полную ссылку `https://<площадка>/tenant/<имя>/`. При вставке полной ссылки tenant заполняется автоматически |
| Tenant | Имя из ссылки `https://<площадка>/tenant/<имя>/` |
| API Token | Cloud Director → меню пользователя → User preferences → Access Tokens → NEW |
| Версия API | По умолчанию «Автоматически»: выбор совместимой стабильной версии из `GET /api/versions`. Ручная версия также проверяется по списку площадки |
| Таймаут | По умолчанию 30 секунд на запрос; допустимо 5–120 секунд |

Отдельные Key ID/Key Secret Evolution, project_id, пароль пользователя и прямой
доступ к vCenter или NSX Manager для этого способа подключения не требуются.
Токен наследует права его владельца. Нужны права чтения выбранных ресурсов и
сетевых сервисов. Генерация собственного API Token требует соответствующего
права в роли пользователя; настройка роли выполняется администратором tenant.

API Token обменивается на временный Access Token перед каждым сканированием и
проверкой подключения. Используется пользовательский API Token. Service Account
с ротацией refresh_token и процедура device_authorization в эту версию не входят.

Основание: [API Token Cloud.ru VMware](https://cloud.ru/docs/vdc/ug/topics/basic-info/basic-info__api-token)
и [отдельный механизм Service Account](https://cloud.ru/docs/vdc/ug/topics/api/api__service-tenant).

## Используемые API

`SITE` — настроенный адрес площадки. После авторизации передаётся заголовок
`Authorization: Bearer <access_token>`. В Accept передаётся выбранная версия API.

| Метод и путь относительно SITE | Назначение |
| --- | --- |
| `GET /api/versions` | Определение поддерживаемых версий до передачи ключа, без авторизации |
| `POST /oauth/tenant/{tenant}/token` | Обмен API Token: form-urlencoded `grant_type=refresh_token&refresh_token=<API Token>` |
| `GET /api/org/` | Проверка доступа к указанному tenant |
| `GET /api/query?type=vm&format=records&filter=(isVAppTemplate==false;isDeleted==false)&page=...&pageSize=128` | Инвентарь ВМ без шаблонов каталога и удалённых записей |
| `GET /api/vApp/vm-{uuid}/networkConnectionSection` | Сетевые подключения, IP/MAC и параметры подключения ВМ |
| `GET /cloudapi/1.0.0/edgeGateways?page=...&pageSize=128` | Инвентарь Edge Gateway |
| `GET /cloudapi/1.0.0/orgVdcNetworks?page=...&pageSize=128` | Сети Org VDC и их параметры |
| `GET /cloudapi/{version}/edgeGateways/{urn}/firewall/rules` | Пользовательские и системные правила Firewall |
| `GET /cloudapi/{version}/edgeGateways/{urn}/nat/rules?page=...&pageSize=128` | Правила NAT |
| `GET /cloudapi/{version}/edgeGateways/{urn}/routing/staticRoutes?page=...&pageSize=128` | Настроенные статические маршруты |
| `GET /cloudapi/1.0.0/firewallGroups/{id}` | Объекты, на которые ссылаются правила Firewall |
| `GET /cloudapi/1.0.0/applicationPortProfiles/{id}` | Профили протоколов и destination ports |

Для сетевых сервисов Edge Gateway версия пути — `1.0.0` для API до 38.1 и
`2.0.0` начиная с 38.1. Сбор этих сервисов предназначен для NSX-T Edge Gateway.
При несовместимости API, отсутствии ресурса или прав результат содержит ошибку;
недоступные данные не подменяются пустым успешным результатом. NSX-V, DFW,
конфигурации гостевых NGFW, динамические маршруты и расчёт эффективной достижимости
пока не поддержаны. При сборе Firewall дополнительно читаются указанные в правилах
группы и профили сервисов; один объект запрашивается один раз за сбор. Ошибка
чтения объекта сохраняется отдельно и не удаляет уже полученные правила.

Справочники: [VM Query](https://github.com/vmware/go-vcloud-director/blob/main/types/v56/constants.go),
[операции vCloud API](https://developer.broadcom.com/xapis/vmware-cloud-director-api/latest/doc/landing-user_operations.html),
[Edge Gateway](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/1.0.0/edgeGateways/get/),
[сети Org VDC](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/1.0.0/orgVdcNetworks/get/),
[Firewall API](https://knowledge.broadcom.com/external/article/401636),
[NAT API](https://knowledge.broadcom.com/external/article/424616),
[Static Routes](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/2.0.0/edgeGateways/gatewayId/routing/staticRoutes/get/).

## Как запустить

1. Выберите или создайте проект.
2. Откройте Настройки → Интеграции → Cloud.ru → VMware.
3. Заполните поля и нажмите «Проверить подключение». Проверяются текущие данные формы;
   пустое поле токена использует сохранённый ключ только для той же площадки и tenant.
   Проверка не сохраняет изменения. После успешной проверки нажмите «Сохранить подключение».
4. Перейдите в Операции → Облачный сбор → Новый сбор и выберите Cloud.ru VMware.
5. Выберите ВМ, Edge Gateway и/или сети Org VDC. Инвентарь выбранных типов
   собирается всегда. Дополнительно можно включить сетевые подключения ВМ,
   Firewall, NAT и статические маршруты шлюзов.
6. Нажмите «Запустить сканирование». Сбор выполняется в фоне. Отмена действует
   после текущего API-запроса; частично собранные ресурсы сохраняются.
7. По умолчанию включено «После сбора VMware автоматически проверить правила
   Edge Firewall». Проверка выполняется после сбора в текущем проекте.
   Для старой выгрузки откройте вкладку «Результат», выберите сбор и нажмите
   «Проверить правила сохранённого сбора»: для этого сеть и ключ не нужны.
8. «Открыть проблемы и результаты проверок» открывает созданный запуск анализа.
   Находки также доступны в общепроектной области «Анализ → Проблемы», а запуск —
   в истории и в отчётах.

Собираются доступные токену ресурсы tenant, без фильтра по отдельному Org VDC.
Запрос ВМ исключает записи `isVAppTemplate=true` и `isDeleted=true`; клиент также
проверяет эти признаки при разборе каждой страницы. Машины внутри шаблонов каталога
не считаются устройствами и не опрашиваются по адресу обычной ВМ.
Пустые группы правил Firewall (`userDefinedRules`, `systemRules`, `defaultRules`)
могут приходить как `null` или `[]`: обе формы сохраняются как пустой список.
Непустые группы, включая системные и правила по умолчанию, сохраняются полностью.
Отсутствие `userDefinedRules` или неверный тип группы остаётся ошибкой сбора.
История, ресурсы, ошибки, список запросов и JSON доступны в разделе сканирований.
Снимок можно экспортировать в JSON. Переключение локального проекта не меняет
проект назначения уже запущенного сканирования.

Статусы: завершено, частично, ошибка, отменено или прервано при закрытии окна.
Сбор и анализ — отдельные операции. Наличие ресурса в инвентаре не означает,
что он проверен. Анализ сохраняет новую ревизию и отчёт, не меняя исходный сбор,
старые отчёты или пользовательские решения. Проверки безопасности гостевой ОС,
NAT и DFW этим запуском не выполняются.

## Где увидеть собранные правила

В **Анализ → Правила и объекты → Все ресурсы проекта · последние снимки**
каждое правило Firewall и NAT отображается отдельной строкой. То же представление
доступно в модели карточки облачного ресурса (инспектор инфраструктуры временно
скрыт в v0.3 по INFRA-001). Правила сохранённых сборов видны без повторного
запроса к облаку. Область «Выбранный запуск» показывает также нормализованные
правила, если открыт запуск облачного анализа.

Для Firewall показаны пользовательские, системные и правила по умолчанию,
действие, состояние, источники, назначения и сервисы. Для NAT показаны тип и
внутренние/внешние адреса; наличие NAT не трактуется как разрешение доступа.
Карточка правила содержит исходные поля API, ID ресурса/сбора и время получения.
После анализа нормализованные правила заменяют соответствующие сырые строки
Firewall в общей таблице; NAT остаётся отдельным типом и не превращается в ALLOW.

## Применяемые проверки и карта

Используется существующий каталог: FW-ANY-ANY, FW-DUPLICATE, FW-SHADOWED,
FW-MERGE-CANDIDATE, FW-LOGGING, FW-COMMENTS, FW-DISABLED. Выбор проверок и требования
логирования/комментариев берутся из «Настройки → Правила». Management-checks к
данным Edge Firewall неприменимы и не запускаются.

Порядок политики: systemRules → userDefinedRules → defaultRules. Сохраняются
действие, направление, active/enabled, семейство IP, логирование и комментарии.
Разрешаются явные IP/CIDR/диапазоны, статические IP_SET и представимые профили
TCP/UDP с destination ports. Динамические группы, недоступные ссылки, source ports,
L7/network context, appliedTo и другие непредставимые условия остаются unknown.
Смешанные IN/OUT/IN_OUT ограничивают попарные выводы. Неполные условия отмечаются
в отчёте; они не заменяются ANY. Старый сбор без дополнительных объектов можно
проверить частично; новый сбор получает группы/профили автоматически.

**Сетевая карта → Карта проекта** использует ту же нормализацию Firewall:
показываются разрешающие/запрещающие и отключённые правила, сервисы/порты,
источник и полнота условий. Неизвестные группы остаются отдельными узлами условий.
Уникальные IP ВМ сопоставляются только внутри известного VDC и подключения;
совпадение адресов/имён других VDC не создаёт связь. NAT не отображается как
разрешение доступа. Выберите связь и нажмите «Правила выбранной связи» для перехода
к её правилам и исходным полям сохранённого API-ответа.

Для анализированного Edge доступен и отдельный режим карты ACL через выбор
результата проверки. Карта описывает заданные условия, а не доказанный сквозной
сетевой путь. Новые отчёты хранятся в существующих runs/items с добавочным
cloud_origin; схема SQLite и содержимое старых записей не переписываются.

API-модели: [GatewayFirewallRule](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/data-structures/GatewayFirewallRule/),
[профили сервисов](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/data-structures/ApplicationPortProfiles/).

## Хранение

API Token хранится в отдельной таблице SQLite, зашифрованный Windows DPAPI для
текущего пользователя. Он не копируется в настройки проверок, историю запусков,
результаты сканирования или экспорт JSON. Access Token существует только в памяти
клиента во время запроса. На другом компьютере/профиле Windows нужно ввести API
Token заново. Пустое поле при сохранении прежнего адреса и tenant сохраняет токен;
для нового адреса или tenant требуется повторный ввод.

Проверка TLS включена. Перенаправления не выполняются. Ошибки не содержат тела
ответа авторизации, токенов или заголовков. Снимки ресурсов содержат реальные
адреса и имена инфраструктуры и сохраняются в локальной базе проекта.

Автотесты используют синтетические ответы API. Проверка на реальной площадке
Cloud.ru требует заполненного подключения и доступного tenant.

## Диагностика подключения

Проверка выполняется последовательно: список версий → обмен API Token → чтение
списка организаций. В настройках выводятся выполненные запросы, выбранная версия
и причина отказа. Ключи, заголовки авторизации и тела ответов туда не попадают.

- **DNS**: имя площадки не определяется. Сверьте символы и порядок чисел с адресной
  строкой открытого Cloud Director; при необходимости проверьте корпоративный DNS/VPN.
- **TLS**: проверьте точность адреса, дату компьютера и доверенные сертификаты
  Windows/корпоративного прокси. Проверка сертификатов остаётся включённой.
- **Таймаут / соединение отклонено**: проверьте доступ к HTTPS, VPN, прокси и таймаут.
- **Неподдерживаемая версия / HTTP 406**: выберите «Автоматически» и сохраните.
  Ранее сохранённая версия `36.1` не заменяется молча: её необходимо изменить.
- **HTTP 400/401 при обмене токена**: проверьте API Token пользователя Cloud Director,
  tenant и площадку. Key ID/Secret из Evolution здесь не используются.
- **HTTP 403 при чтении ресурсов**: проверьте права владельца ключа на эти ресурсы.

Автовыбор использует совместимые версии 36.1–39.1 и предпочитает версии без
признака deprecated. Предварительные alpha/beta-версии не выбираются. Если
совместимых версий нет, проверка завершается ошибкой до отправки ключа.

Основание: [порядок аутентификации Cloud.ru](https://cloud.ru/docs/vdc/ug/topics/api/api__auth),
[GET SupportedVersions](https://developer.broadcom.com/xapis/vmware-cloud-director-api/latest/doc/operations/GET-SupportedVersions.html),
[HTTP 406 и устаревшие версии API](https://knowledge.broadcom.com/external/article/429376/error-clienterrorexception-http-406-not.html).
